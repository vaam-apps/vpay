# Dashboards

Three Grafana dashboards for the operators of vpay, as code: the JSON in this folder is the dashboard, and **it is
generated** by the Python scripts in [`tools/dashboards/`](../../tools/dashboards/) (`sh tools/dashboards/generate.sh`;
standard library only). Edit the script, never the JSON or this page: CI regenerates every file and fails on any
difference or untracked file. A panel is one call of `timeseries`, `stat` or `text`.

They read the metrics the services export over OpenTelemetry ([`vpay-telemetry`](../../backends/crates/vpay-telemetry/README.md),
[ADR-0039](../../docs/adr/0039-opentelemetry-through-the-sdk-and-generated-dashboards.md)) once a collector has put them in a
Prometheus-compatible store (Grafana's Prometheus data source, an OpenObserve instance's PromQL endpoint, Mimir,
VictoriaMetrics, and so on). The names are `vpay_core::metrics`'s own, so the Prometheus listener (`/metrics`) and these
dashboards read one vocabulary.

## What these dashboards do not claim

**A panel counts what the code recorded, nothing more.** The rail panels count calls vpay made to the host a rail is
configured with. A rail configured against a stub host reports like a live one, and a rail whose adapter is not written
reports its `not_implemented` error. Which rails have been called live, and when, is in
[`docs/status.md`](../../docs/status.md), and this folder never says a rail works. An empty panel means no such event
happened, not that it is healthy.

| File | Dashboard | For |
|---|---|---|
| [`vpay-service.json`](vpay-service.json) | vpay: service | For the HTTP API: traffic, errors, latency and the running builds |
| [`vpay-rails.json`](vpay-rails.json) | vpay: rails, charges and webhooks | For payment rails, the charge state machine, callbacks and the webhook backlog |
| [`vpay-platform.json`](vpay-platform.json) | vpay: job queue and database | For the job queue, the database pool and the exporter itself |

## Importing

Grafana 10 or later. In Grafana: *Dashboards, New, Import*, upload each file, and pick the Prometheus data source. Or
from a shell, with a service account token in `GRAFANA_TOKEN` (never in a file of this repository):

```sh
for f in deploy/dashboards/*.json; do
  curl -sS -X POST "$GRAFANA_URL/api/dashboards/db" \
    -H "Authorization: Bearer $GRAFANA_TOKEN" -H 'Content-Type: application/json' \
    -d "{\"dashboard\": $(cat "$f"), \"overwrite\": true}"
done
```

Every dashboard has a **Data source** variable and a **Service** variable (the `job` label, which a collector sets from
`service.name`; `vpay` unless `OTEL_SERVICE_NAME` says otherwise). Names are the Prometheus names: a collector turns a
histogram `vpay_http_request_duration_seconds` into `_bucket`, `_count` and `_sum`. **Unverified:** that the deployment's
collector and store apply exactly this naming (it is the OpenTelemetry to Prometheus translation as specified, and the
vocabulary's units are chosen so it appends no suffix of its own); a store with another scheme needs the queries
adjusted. **Unverified:** that Grafana imports these files on the version a deployment runs; they use only `timeseries`,
`stat` and `text` panels and the Prometheus data source.

## vpay: service

The HTTP API: traffic, errors, latency, classified errors and the running builds. Generated by tools/dashboards/service.py.

| Panel | What it watches, and what to do |
|---|---|
| `Request rate by route` | Requests per second by route pattern (never the concrete path), the health and metrics listeners left out. |
| `Requests by status class` | Requests per second as 2xx, 3xx, 4xx and 5xx, stacked. |
| `5xx ratio` | The share of responses that were 5xx, over the range: the service or its database failing the caller. |
| `4xx ratio` | The share of responses that were 4xx. A jump after a deployment is usually a merchant on an old contract or a credential that expired. |
| `Classified errors by category, code and severity` | Errors the service classified (ADR-0011) per second. A category says whose problem it is: InvalidRequest and Authentication are callers, Rail and Storage are dependencies, Internal is a fault. |
| `Page-severity errors in the range` | Errors at the severity that wakes someone. Orange at one: it is the counter an alert on 'a page happened' reads. |
| `Latency by route (p50, p95, p99)` | Response time quantiles over every route: routing, authentication, the handler and the error renderer. |
| `p95 latency by route` | The 95th percentile of each route: where a slow call is. A route with few requests has a noisy quantile. |
| `Running builds` | How many processes report each version and git sha. More than one row during a rollout is expected; a row that stays after it is a pod that did not restart. |
| `Reading this dashboard` | These panels come from the metrics the service exports over OpenTelemetry. A metric exists only for what the code has recorded: **a panel that is empty means no such request has happened, not that it is healthy.** Which parts of vpay run against a real rail and which against a stub is in `docs/status.md`, not here. |

## vpay: rails, charges and webhooks

Calls to the payment rails, the charge state machine, provider callbacks and the webhook delivery backlog. Counts calls to whatever host a rail is configured with: it does not say a rail works. Generated by tools/dashboards/rails.py.

| Panel | What it watches, and what to do |
|---|---|
| `What a rail panel does and does not say` | **These panels count calls vpay made to the host a rail is configured with, and what came back.** A rail configured against a stub host (a WireMock container in the dev, demo and end-to-end stacks) reports exactly like a live one, and a rail whose adapter is not written reports its `not_implemented` error here. Nothing on this dashboard says a rail *works*: `docs/status.md` says which rails have been called live, and when. The calls are port calls, not wire requests (`docs/reference/vpay-core.md`). |
| `Rail calls by provider and operation` | Calls per second to each rail, by port operation (prepare, submit, query_status, refund, account_holder_name, ensure_callback_endpoint). |
| `Rail call errors by provider and kind` | Calls that failed, per second, by rail and by error code (the same words as provider_requests.error_kind). not_implemented is an adapter that does not do this yet, not an outage. |
| `Rail call error ratio by provider` | The share of each rail's calls that failed. A rail with a handful of calls has a ratio that jumps on one failure; read it with the rate above. |
| `Rail call latency by provider (p50, p95, p99)` | Wall-clock time of one call to a rail, per provider. Mobile-money rails are slow in a way an HTTP route is not. |
| `Charge transitions by new state` | Charges entering each state per second, by rail. A charge is the unit that moves through submitting, submitted, pending, unresolved, succeeded and failed; the payment intent's own status is not exported (it has no index to count by). |
| `Charge transitions (from, to)` | Each edge of the charge state machine per second. The edge is the alertable quantity: submitted to failed is a decline, pending to unresolved is a poll ladder that ran out. |
| `Charges that went unresolved in the range` | Charges whose poll ladder ended with no answer from the rail. Each one needs a human: orange at one. |
| `Charges that failed in the range` | Charges that ended failed: a rail declining or an error. Read with the error panels above; a payer who declines is not an incident. |
| `Provider callbacks by verdict` | Callbacks received for a charge vpay holds, by what the rail's check said. invalid is a wrong signature (a misconfigured secret, or a forgery); no_secret is a rail that signs and a deployment with no secret set; not_checked is a rail whose callbacks vpay does not check. |
| `Webhook backlog` | Deliveries owed an attempt (state pending). It includes deliveries waiting for a retry rung that is not due yet, so it is a size, not a lateness: read it with the overdue age beside it. Orange at 1,000, red at 10,000. |
| `Oldest overdue delivery` | How long the most overdue pending delivery is past its next attempt; zero when none is due. A value that keeps growing is a worker that is not delivering. Orange at 5 minutes, red at 30. |
| `Webhook backlog over time` | The two backlog numbers together: a burst rises and falls, a stalled worker rises with the overdue age. |
| `Webhook delivery attempts by outcome` | Delivery attempts per second as succeeded, retry (the ladder has a rung left) or exhausted (parked for a human, docs/runbooks/webhook-delivery-failures.md). |
| `Deliveries exhausted in the range` | Deliveries whose retry ladder ran out. Each one is a merchant who did not get an event and needs a person: orange at one. |
| `Account-holder lookups by outcome` | GET /v1/account_holders answers per second: found, not_found, unsupported (no rail could answer) and error (a rail or a malformed number). No label carries the number or the name. |
| `Callback endpoint checks by state` | What the ensure_callbacks pass found at each rail: present is healthy; created more than once means something deletes the endpoint; drifted, foreign and missing need a person. |

## vpay: job queue and database

The job queue, the database pool as the service sees it, and the OpenTelemetry exporter's own counters. Generated by tools/dashboards/platform.py.

| Panel | What it watches, and what to do |
|---|---|
| `Queue behind by` | Seconds since the next queued job was due, over the whole table. Negative is normal on an idle deployment (the next job is in the future); the panel is clamped at zero for reading. A value that grows is workers not claiming. Orange at 60 s, red at 5 minutes. |
| `Queue age over time` | The raw gauge, negative values included: the line sits below zero when the queue is idle and rises above it when jobs are due and unclaimed. |
| `Jobs claimed by kind` | Jobs this fleet claimed per second, by kind: the shape of the work (polls, deliveries, fan-out, sweeps). |
| `Jobs completed by kind and outcome` | How claimed jobs ended: terminal (done), retry, dead_letter (parked for a human) or lost (the lease moved before the worker could settle). |
| `Dead-lettered jobs in the range` | Jobs parked at run_at infinity for a human. Orange at one: each is work the system gave up on. |
| `Connection pool by process` | Connections of each process's pool, idle and in use, against the configured maximum. A process at its maximum makes requests and jobs wait for a connection. |
| `Busiest pool in use` | The largest share of any process's pool checked out right now. Orange at 70%, red at 90%: raise the maximum or add a replica before callers queue. The server's own load (locks, replication, disk) is PostgreSQL's exporter, not this service's. |
| `Storage errors in the range` | Classified errors of category Storage (PostgreSQL unreachable, a query failed, a migration broke). Orange at one. |
| `Telemetry exports by signal and result` | Export requests per second to the collector, by signal and result. failed is a collector that refuses or does not answer after retries: look at its address, its credential header and the network policy. This series does not exist when telemetry is off. |
| `Telemetry dropped by signal` | Spans, logs and metric series the exporter dropped (a full bounded queue, or the cap on distinct series). The exporter never blocks a request: it drops. A band here says the other panels are incomplete. |
| `What is not here` | PostgreSQL's own metrics (replication lag, locks, disk, cache hit ratio) come from the database's exporter or its operator, not from this service. The pool panels show the service's view: the connections it holds. |

## What to alert on

Alert rules are the operator's, and none is shipped. Starting points from the thresholds above: `Queue behind by` over
300 s; `Oldest overdue delivery` over 1,800 s; `5xx ratio` over 1% for 10 minutes; `Busiest pool in use` over 90% for
10 minutes; `Page-severity errors in the range` above zero; `Deliveries exhausted in the range` above zero.
