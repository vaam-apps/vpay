READ THIS.

  * This chart has never been applied to a cluster by anyone. Its entire
    evidence is `helm lint`, `helm template` and `kubeconform` in CI. Nothing
    has verified scheduling, the probes, readOnlyRootFilesystem, the
    NetworkPolicy, the PodDisruptionBudget during a rolling restart, or
    whether the ingress controller honours `limit-rps`.

  * The liveness probes point at {{ .Values.observability.livenessPath }} on port {{ .Values.observability.port }} — the
    observability listener (`--observability-bind`), which both binaries bind
    as of 2026-09-03. Both `tests/cli.rs` suites prove /livez and /metrics
    answer there and 404 on the traffic port. An image built BEFORE that
    (anything older than this chart's appVersion) has no such listener and
    will be restarted in a loop by the kubelet: pin `images.*.digest`, and
    check `docs/status.md`.

  * This chart creates no Secret and no database. These must already exist:
      Secret/{{ .Values.database.existingSecret }} (key {{ .Values.database.existingSecretKey }}) — the Postgres URL
      Secret/{{ .Values.signingKey.existingSecret }} (key {{ .Values.signingKey.key }}) — the RS256 signing key
      Secret/{{ .Values.envelopeKeys.existingSecret }} (keys {{ .Values.envelopeKeys.current }}, {{ .Values.envelopeKeys.next }}) — the signed /v1 transport's two Ed25519 response seeds; hand merchants both PUBLIC halves
      Secret/{{ .Values.rails.existingSecret }} — the rail credentials, one key per ${VAR} in the config

  * Rotating the signing key is restart-based, and rolling back to a retired
    kid is exit 78, not a degraded start.
{{ if .Values.server.autoscaling.enabled }}
  * An HPA now owns -server's replica count. Two consequences nothing else
    will tell you about. Every replica holds a pool of up to 10 Postgres
    connections, so the ceiling this release can ask for is
    ({{ .Values.server.autoscaling.maxReplicas }} + {{ if .Values.management.enabled }}{{ .Values.management.replicaCount }}{{ else }}0{{ end }} + {{ .Values.worker.replicaCount }}) x 10 = {{ mul (add (int .Values.server.autoscaling.maxReplicas) (ternary (int .Values.management.replicaCount) 0 .Values.management.enabled) (int .Values.worker.replicaCount)) 10 }} against a
    database.maxConnections of {{ .Values.database.maxConnections }} (the "connection-budget" guard checks
    this at template time; nothing re-checks it when the HPA actually
    scales). And scale-down evicts pods mid-request unless
    behavior.scaleDown.stabilizationWindowSeconds is well above the
    process's own {{ .Values.shutdownGraceSeconds }}s drain.
{{- end }}
{{ if .Values.management.enabled }}
  * This release runs the surfaces SPLIT (ADR-0022, status: Proposed).
    -server serves the merchant API and /svc/v1, -management serves /dash/v1;
    neither serves the other's. Two things that are easy to get wrong:

      - /dash/v1 is only reachable by whatever you have pointed at
        Service/{{ include "vpay.fullname" . }}-management.{{ if not .Values.route.enabled }} This release publishes no
        HTTPRoute for it (route.enabled is false), so nothing outside the
        cluster reaches it yet.{{ end }}{{ if and .Values.route.enabled .Values.networkPolicy.enabled }} The HTTPRoute publishes it AND the
        NetworkPolicy restricts who may reach the pod — check both agree.{{ end }}
      - POST /v1/oauth/token is served by -server ONLY. It mints the
        MERCHANT credential. /svc/v1, the door the service that pairs console
        keys (vaam) walks through, is on -server too, at the same
        Service/{{ include "vpay.fullname" . }}:{{ .Values.service.port }} origin merchants use, and is published
        by no HTTPRoute or Ingress: with networkPolicy on, that caller must be
        listed in networkPolicy.serviceIngress.peers or the CNI drops it.
        /dash/v1 and /svc/v1 are both served only when the overlay carries a
        dashboard: block; without one this release has no console at all.
{{- end }}
{{ if .Values.dashboard.enabled }}
  * The dashboard's staff sign-in is configured in two places that must agree, and Helm sees only one.
    dashboard.clientId / redirectUri / scope are this chart's; the overlay's dashboard_client block
    (and staff_auth, both or neither) is overlay text. The cookies are __Host- prefixed and Secure: reach
    the dashboard over https{{ if hasPrefix "http://" .Values.dashboard.publicOrigin }} — dashboard.publicOrigin is {{ .Values.dashboard.publicOrigin }}, which only a browser on localhost will keep a cookie for{{ end }}, or the sign-in does not stick.
{{- if .Values.dashboard.ssoIssuer }}
  * Single sign-on is offered on /login: dashboard.ssoIssuer is {{ .Values.dashboard.ssoIssuer }}. It must be the
    issuer staff_auth.sso.issuer carries. Register {{ .Values.dashboard.publicOrigin }}/api/auth/sso/callback at the
    provider and write the same string as staff_auth.sso.redirect_uri. That is NOT dashboard.redirectUri, which is
    never visited. Without staff_auth.sso in the overlay (and human_login served) the button is not drawn.
{{- else }}
  * Single sign-on is not offered: dashboard.ssoIssuer is empty. If the overlay writes staff_auth.sso, set it
    to that block's issuer, or /login names the variable and draws no button.
{{- end }}
