# CrateStack — the first transport: mounting `searchPaymentIntents` (2026-09-13, Lane C)

**Corrects [2026-09-11-search-payment-intents.md](2026-09-11-search-payment-intents.md), which said "Nothing serves it."** That is no longer true: `vpay_db::Repositories::dashboard_procedure_router` mounts CrateStack's generated `procedure_router`, and `POST /dash/v1/$procs/searchPaymentIntents` answers over HTTP against a real Postgres. This page is the account of how, read from the CrateStack 0.12.0 sources before any code was written
(`docs/plans/2026-09-13-dashboard-nav-notes/transport.md`) and measured after.

## The two rules that had to hold, and how each was kept

**1. `procedure_router`, never `router()`.** `router()` merges `model_router(...)` — the generated CRUD for every one of this schema's eighteen models, creates/updates/deletes included, whether or not anything routes it — with `procedure_router(...)`
(`cratestack-macros-0.12.0/src/include/server/axum_module/router_fn.rs`). `procedure_router` is the same generated function with that merge removed, emitted `pub` with the same arguments minus `body_limit_bytes`
(`axum_module.rs:138`). `vpay_db::schema::dashboard_procedure_router` calls it, and only it.

Proven rather than asserted: `schema::tests::no_generated_model_route_is_mounted_only_the_one_procedure_is` walks every one of the eighteen models' generated `list`/`create` path (`/{plural}`) and `get`/`update`/`delete` path (`/{plural}/{id}`), across `GET`/`POST`/`PATCH`/`DELETE`, against the router this crate actually builds, and asserts each answers this crate's honest `404` — the mechanical version of `DASH_ROUTES`' own reason for keeping a route table (`vpay_api::dash`'s doc: axum 0.8 cannot enumerate a built `Router`). Decisive: changing the call from `procedure_router(...)` to `router(...)` reddened every one of the seventy-two assertions at once, turning the model paths' answers from `404` into something else (a `500` from the deliberately-unreachable lazy pool the test uses, since a policy-admitted read then tried to run a statement) — the test does not care what the wrong answer is, only that it stops being `404`.

**2. Never mint a system context for a request.** `vpay_db::persistence::system_context()` is the only context in this crate for which `is_system()` is true, and `auth().isSystem()` guards every write policy in the schema — a request-scoped context built from it would satisfy all of them. The transport's `AuthProvider` is `vpay_db::dashboard_transport::ExtensionAuthProvider`, which builds a context with `CratestackContext::with_principal(...)` from a plain tenant id string, and never calls `system_context()`. `dashboard_transport::tests::a_resolved_tenant_becomes_an_authenticated_tenant_carrying_context` asserts `!ctx.is_system()` explicitly, alongside the positive claim (`ctx.tenant_id()` and `ctx.is_authenticated()`).

## The seam that supplies the tenant, and why it crosses a crate boundary the way it does

`cratestack::AuthProvider` (`cratestack-core-0.12.0/src/context.rs:92`) has a blanket impl for a header-only closure, but this transport needs the tenant `vpay_api`'s own `require_dashboard_procedure_token` middleware already resolved onto the request's **extensions** — the same `vpay_api::dash::DashboardTenancy` [ADR-0018](../../adr/0018-cross-tenant-admin-reads.md) added — not its headers. `ExtensionAuthProvider` implements the trait directly against `RequestContext::extensions` instead.

Crossing the crate boundary without widening it: `vpay-api` must not depend on `cratestack` directly (`docs/reference/vpay-db/cratestack.md`'s "taken here and NOWHERE else in the workspace"), so it cannot construct a `CratestackContext` itself. `vpay_db::DashboardAuthFn` is `Arc<dyn Fn(&axum::http::Extensions) -> Option<String> + Send + Sync>` — a plain tenant-id closure, built in `vpay-api` from `extensions.get::<dash::DashboardTenancy>()`, that `vpay-db` alone turns into a full `CratestackContext`. Neither crate learns something it should not: `vpay-api` never sees `CratestackContext`, and `vpay-db` never sees `DashboardTenancy`.

`vpay_db::Repositories` gained one new method for this, `dashboard_procedure_router(&self, auth: DashboardAuthFn) -> cratestack::axum::Router`, deliberately **not** built on `Repositories::op_store_pool` — that accessor's own doc says "not a general escape hatch: a new `sqlx::query!` behind this call is a repository method that was not written," and building a second `Cratestack` runtime from the raw pool would be exactly that pattern reused for a second purpose. The method instead reuses `PgRepositories::cs`, the `Cratestack` handle every repository method already runs its own queries through — one pool, one `Cratestack`, as before this lane.

## Why a second, `POST`-only middleware rather than widening `require_dashboard_token`

CrateStack's generated procedure transport is `POST /$procs/<name>` unconditionally (`cratestack-macros-0.12.0/src/axum/procedure/route_attrs.rs`). `require_dashboard_token`'s method check (`dash::required_scope`) refuses every method but `GET`/`HEAD` on `/dash/v1` — the single place ADR-0008's "no write reaches a handler" property lives — so reusing it verbatim would refuse the very `POST` this transport answers.

`require_dashboard_procedure_token` is a new, narrower function: `POST` only, on `/dash/v1/$procs/searchPaymentIntents` alone (nothing else is mounted there). It shares `resolve_dashboard_tenancy` — the token validation, merchant-claim check, scope check, staff re-read and ADR-0018 tenancy resolution — with `require_dashboard_token`, extracted from that function's body without changing its own observable behaviour: all 21 pre-existing cases in `backends/tests/integration/tests/dashboard_read_surface.rs` pass unchanged, including the ADR-0018 admin/cross-tenant ones (`an_admin_reads_a_merchant_other_than_its_own`, `a_non_admin_cannot_move_the_tenant_with_the_query_parameter`). `/dash/v1`'s own boundary — every method but `GET`/`HEAD` refused, in code and in its own tests — is untouched.

Mounted as its own nest (`router.nest_service(dash::DASH_NEST, dash_procs)`), not merged into the existing `dash` nest, for a mechanical reason rather than a stylistic one: `vpay_db::Repositories::dashboard_procedure_router` returns `axum::Router<()>` (CrateStack's generated function calls its own `.with_state(...)` internally, over its own state type), while the rest of `vpay_api::router` stays `Router<AppState>` until this function's own final `.with_state(state)`. `Router::merge`/`Router::nest` both require the same state type on both sides; `Router::nest_service` treats its argument as an opaque `tower::Service` and does not care what it closed over.

## Proof over HTTP, and what it does and does not claim

`backends/tests/integration/tests/dashboard_procedure_transport.rs` boots the real `vpay_api::router` on a real socket over a real Postgres, exactly as `dashboard_read_surface.rs` does for the hand-written `GET` routes:

- `the_procedure_answers_the_callers_own_merchant_over_http` seeds two merchants' intents, calls `POST /dash/v1/$procs/searchPaymentIntents` with a real dashboard token, and asserts the page carries the caller's own merchant's two rows, newest first, and never the other merchant's — the `POST` surface's version of `dashboard_read_surface.rs`'s `the_dashboard_lists_only_the_merchant_it_is_bound_to`.
- `an_unauthenticated_caller_is_refused` asserts the same call with no bearer token is a `401`, before `require_dashboard_procedure_token` reaches CrateStack's own policy at all.

2 passed, 0 ignored.

The tenant-mismatch mutation is `vpay-db`'s own, not repeated here as a second container start: replacing `search_payment_intents.rs`'s `WHERE merchant_id = $1` with `WHERE $1::TEXT = $1::TEXT` reddens `against_postgres::the_page_is_the_tenants_own_rows_filtered_and_bounded`, which reported `pi_b_only` appearing in `merchant_a`'s page (`left: ["pi_b_only", "pi_a_new", "pi_a_old"], right: ["pi_a_new", "pi_a_old"]`) before the mutation was reverted. That test is a property of the procedure body, shared by every transport that ever calls it, so it is exercised once rather than duplicated per transport.

**What this is not.** One procedure, one route, `GET`-equivalent read access mediated by a `POST`. `/dash/v1`'s hand-written routes are unchanged. No write is reachable through this or any other CrateStack-mounted surface in this workspace — see the routing-table proof above. The dashboard's frontend does not read through this yet; nothing in Lane C touches `frontends/apps/dashboard`.
