# Verification log — 2026-09-12, `@vaam-apps/ui` 0.1.1 → 0.1.2

Last verified: 2026-09-12, on branch `claude/vaam-apps-ui-012`, stacked on
the Storybook restoration
([2026-09-12-storybook-restored.md](2026-09-12-storybook-restored.md)) —
which is what made two of the three findings below visible at all.

## What the release changes

An opt-in `light` theme; `dark` keeps `default: true`, so an app that pins
`data-theme="dark"` — which both of ours do — renders exactly what it did.
`dist/styles/theme.css` grows 17 286 → 51 369 bytes. Fonts move from Inter
Variable to IBM Plex.

## What this note claims, and what it does not

It claims both apps build, typecheck, lint and test green on 0.1.2, that the
checkout's 22 payer-facing screens still clear WCAG AA in a real browser, and
that three things in **this** repository needed adapting. **None of the three
is a defect in the release**; two are our own harness assuming one theme, and
the third is an upstream accessibility fix our test was pinning against.

It does **not** claim the light theme works: nothing renders it. Both apps
pin `data-theme="dark"` in their layout, no screen offers a switch, and the
browser a11y gate measures the dark theme only. **A light-theme screen has
never been rendered or measured here.**

## Three adaptations

### 1. `styling-gate.test.ts`, both apps — one theme assumed

`--color-base-100` now resolves to two values (`#0a0b0d`, `#fcfcfd`) and the
case asserted `new Set(["#0a0b0d"])`.

Rewritten to read the permitted set from the package's own `theme.css`. That
is **stricter** than the literal, not looser: the failure this case exists to
catch is `themes: false` being dropped from `globals.css`, which lets stock
daisyUI emit its own `--color-base-100` — and daisyUI authors in `oklch()`
while this package authors in hex, so a leak now fails on set membership
**and** on an explicit `oklch` assertion that names the failure mode.

Mutations, all reverted: `themes: false` dropped (1 failed), the `@source`
line dropped (1 failed), the theme `@import` dropped entirely (2 failed).

### 2. `themeColours`, both apps — a flat map across two themes

This is the one worth reading. Every `--state-*` token is declared twice in
0.1.2 — `--state-danger-fg` is `#fca5a5` under `dark` and `#a80f35` under
`light`. The helper keyed a `Map` by variable name, so the later block
silently won, and `outcome-contrast.test.ts` compared the **light**
foreground against a background composited over the **dark**
`--color-base-100`. It reported the payment-outcome banners at **2.55:1,
2.61:1 and 2.76:1** against AA's 4.5:1, and the hand-computed reference moved
16.34 → 17.52.

**Nothing was wrong with the theme. The harness could not represent two of
them**, and the pair it measured is painted on no screen.

It was told apart by disagreement: `just test-storybook`, which measures
painted pixels in a real browser, passed those same three outcome screens
throughout. **The browser was right and the token model was wrong** — which
is the clearest argument this repository has produced for keeping both kinds
of check.

`themeColours` now takes a `theme` (default `"dark"`, what both apps pin) and
skips declarations an enclosing selector pins to a different one. Forcing
`theme: "light"` fails 4 of the 7 outcome cases, so the scoping is asserted
rather than assumed.

### 3. `StatusPill` drops `role="img"` — an upstream fix, not a break

0.1.2 removes the synthetic `role="img"` + `aria-label` and lets the
accessible name fall out of content. The package's own note gives the reason:
the `img` role flattens the subtree, so a pill's `detail` text rendered
visually and was announced to **nobody**.

`payments-table.test.tsx` asserted the old mechanism. It now asserts the same
two facts — that a status's label comes from the shared
`PAYMENT_STATUS_SYSTEM` and that the raw status is still announced — off the
rendered text instead of off an attribute, still read from the table rather
than typed as literals. Its own mutation note was re-run: pointing
`processing`'s row at `succeeded`'s meta fails it (1 failed / 6 passed).

## A wrong finding, retracted before it shipped

Mid-investigation this note would have said 0.1.2 **removed**
`createStatusPill`: a grep of `dist/index.d.ts` and `dist/index.js` returned
zero. It is there — in `dist/components/status/status-pill.d.ts`, reached
through the barrel — and `pnpm --filter @vpay/dashboard typecheck` passing is
what contradicted the grep and forced the re-check. A grep over a barrel file
proves nothing about a re-exported symbol.
