## The headline, first

**Nothing here moved a capability, and nothing in it may be read as "refunds
work".** No rail has ever executed a refund. `mtn_momo::refund` is MTN's
Disbursements `transfer`, WireMock-proven and rail-unproven — MTN's
Disbursements product has never been called from this repository and **no REAL
credential for it exists in this project**. `orange_money::refund` is a
declared `NotImplemented` token and answers a merchant `501`. Neither rail
answers `Unsupported`. **Nothing settles a `pending` refund** — the provider
port has no refund status read and there is no refund poll ladder (RFC-0003
open question 8, open) — so every refund the five `/v1` routes can create
stays `pending` for ever, and `invoices.amount_refunded` never moves in any
deployment.

**No banner addendum was earned and none was added.** See § "What this pass
refused to change".

### 5. CI never ran the Rust live refund suite that three parity rows cite

The one finding on this pass that is not a documentation bug.

`.github/workflows/ci.yml`'s live-stack job is `just sdk-live` "split into its
two halves so a failure names the SDK". `just sdk-live` runs
`cargo nextest run -p vpay-sdk --features live-stack --test live_invoices
--test live_refunds`. The CI split ran **`--test live_invoices` only**, and
`live_refunds` is a separate `[[test]]` target with
`required-features = ["live-stack"]` — so no CI job ever compiled that binary,
let alone ran it.

Meanwhile `docs/sdks/parity.md` marks three rows ✅ naming
`live_refund_lifecycle` and `live_refund_destination_refusals` as their
proving tests. **`cargo xtask verify-sdk-parity` proves a test NAME exists and
never that anything runs it** (issue #122), so it passed — 603 proving tests —
with three rows resting on a binary nothing built.

The Node half was covered by accident: `vitest.live.config.ts` globs
`src/**/*.live.test.ts`, which picked up `refunds.live.test.ts` the day it
landed. The CI step was still called "invoice lifecycle".

Fixed: the Rust step names both targets and both steps are renamed.
`cargo test -p vpay-sdk --features live-stack --test live_refunds --no-run`
compiles here. **The suite itself was NOT run on this branch** — it needs the
compose stack this branch's agents were told not to disturb, and a
pre-existing `vpay-demo` stack is on port 8080. `parity.md` gained a "Not that
any gate runs the test a ✅ row names" caveat recording the measurement.

## What is still owed, after all of it

1. **A refund poll ladder.** RFC-0003 open question 8, open. The port has no
   refund status read, so `Settlement::apply_refund_succeeded` has **no
   caller** and no refund can leave `pending`. Everything below depends on it.
2. **An event on the refund settlement.** `apply_refund_succeeded` takes a
   `refund_id` and nothing else — no `event_id`, no wire object — where
   `apply_succeeded` takes an `InvoicePaidEvent`. A merchant told `pending` at
   creation would learn nothing when the refund succeeded. Nothing provokes it
   today because nothing settles a refund at all.
3. **Invariants 1-4 asserted on a schedule.** None is. Invariant 2 is
   _computable_ in two independent implementations that a test checks against
   each other, which is a different claim.
4. **Invariant 4's second guard.** One guard, not two: `apply_succeeded`'s
   compare-and-swap. A deterministic ledger transaction id, or a `kind` column
   plus a partial unique index on `charge_id`, would add one. Which — if any —
   is a maintainer decision, recorded in
   `vpay_core::ids::ledger_transaction_id`'s own doc.
5. **A first real MTN Disbursements call.**
   [../../flows/adapter-mtn-momo.md](../../flows/adapter-mtn-momo.md) § "Not
   proven" is the list of what it has to check.
6. **An Orange transfer specification.** Item 5 of
   [../../flows/adapter-orange-money.md](../../flows/adapter-orange-money.md)'s
   "To confirm with Orange Cameroun".
