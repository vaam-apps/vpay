## Item 4: `scan:live` runs every ten minutes, not hourly

`SCAN_INTERVAL` in `vpay_worker::handlers` is `Duration::from_secs(10 * 60)`,
and the handler reschedules itself with it. It has been ten minutes since the
job was written: the constant entered the tree in `c2b0d28`, Step 4
(2026-09-03), with that value. So "hourly" was wrong from the day it was
written.

RFC-0013 named one place; three said it. Each now carries a dated note:

| Place                                                                                       | What it said                      |
| ------------------------------------------------------------------------------------------- | --------------------------------- |
| [../../flows/reconciler.md](../../flows/reconciler.md) § Status, the enqueue bullet         | "The hourly `scan:live` job"      |
| [../../flows/crash-safety.md](../../flows/crash-safety.md), "What Step 4 adds"              | "The hourly `scan:live` backstop" |
| [../../runbooks/worker-queue.md](../../runbooks/worker-queue.md), parked `poll_charge` rows | "the hourly backstop scan"        |

Every other "hourly" in the tree was checked and is right: the housekeeping
`sweep:expired` job (`SWEEP_INTERVAL`, one hour) and the escalated poll of an
`unresolved` charge (`UNRESOLVED_POLL_INTERVAL`, one hour).

## Item 5: no MTN page says MTN requires, or has, an IP-allowlisted callback host

`vpay-config`'s doc comment on `ProviderHost::callback_url` justified the
per-rail override with "an IP-allowlisted host — MTN requires one,
`Capabilities::requires_ip_allowlist`". MTN's pages, read on 2026-10-22
through the HTML widgets they embed:

- the callback page
  (<https://momodeveloper.mtn.com/api-documentation/callback>, widget
  `c0m2f.html`) names no allowlist. Its one rule about the host is that the
  `X-Callback-Url` "must be hosted on the same domain specified when creating
  the API user", the `providerCallbackHost`;
- the best practices (<https://momoapi.mtn.com/content/html_widgets/j2w89.html>,
  the page RFC-0013 cites) list "Services Requiring IP Whitelisting":
  Disbursements / Transfers, Remittances / Transfers, Collections /
  Pre-Approval and Dynamic Journey Services. RequestToPay is not on the list,
  and the page names no callback host. It does not say whose addresses are
  whitelisted; its advice to communicate in advance when adding or changing IP
  addresses reads as the partner's own.

So the override keeps a sourced reason, MTN's per-API-user callback host, and
loses the unsourced one. The same idea was in seven more places, mostly as
"MTN additionally allows an IP-allowlisted callback host of its own". Each is
corrected, with a dated note wherever the file's format allows one:

| Place                                                                              | Now                                                                                                                                                         |
| ---------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `vpay-config/src/config.rs`, `ProviderHost::callback_url`                          | the separate-ingress shape and MTN's registered `providerCallbackHost`; a dated note                                                                        |
| [../../reference/rails.md](../../reference/rails.md), the callback URL contract    | a callback host of the deployment's choosing, MTN's on its registered domain                                                                                |
| `deploy/helm/vpay/values.yaml`, `ingress.provider.sourceRange`                     | a rail's egress ranges, if an operator is given them; a dated note                                                                                          |
| the same file, `ingress.provider.servedElsewhere`                                  | "a callback host of its own", without "IP-allowlisted"                                                                                                      |
| `deploy/helm/vpay/templates/ingress-provider.yaml`                                 | the same as `sourceRange`, and a dated note                                                                                                                 |
| `deploy/helm/vpay/README.md`, "Turning it off is defensible"                       | `providers[].callback_url`, MTN's registered domain; a dated note                                                                                           |
| `deploy/helm/vpay/templates/_validate.tpl`, `provider-callback-routable`'s message | its example "an IP-allowlisted host of the rail's own" is now "a callback host of the deployment's own" — wording only; `helm-check` matches guards by name |
| `backends/tests/conformance/wiremock/mtn/mappings/requesttopay.json`, the comment  | the registered `providerCallbackHost`; a dated note                                                                                                         |

**`requires_ip_allowlist: true` on `mtn_momo` stays,** and now says why it may
be right: the best practices list Disbursements / Transfers, which is what
`refund` calls. The flag has no doc comment in `vpay-provider` and no code
path reads it beyond seeding `providers`; that is unchanged.

  `vpay-config` and `vpay-adapter-mtn-momo`; those two crates were compiled,

  onboarding conversation answers; this page says only what MTN's public pages
  say, and that none of them supports the old sentence.
- `docs/plans/**` is left as written, as #319 left it: plans are history.
