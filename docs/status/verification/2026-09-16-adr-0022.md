### A real defect found and fixed by this observation, not reasoned about

The first build (before `HOSTNAME=0.0.0.0`/`PORT=3000` were added to the
runner stage's `ENV`) started and answered on the **mapped** port
(`docker run -p` worked) but refused every connection to `127.0.0.1` from
**inside** the container — exactly what the `HEALTHCHECK` and a kubelet's
own probe both dial:

```
$ docker exec vpay-dashboard-probe-run node -e "fetch('http://127.0.0.1:3000/healthz')..."
ERR TypeError: fetch failed
  ... Error: connect ECONNREFUSED 127.0.0.1:3000

$ docker exec vpay-dashboard-probe-run cat /etc/hosts
127.0.0.1  localhost
172.17.0.5 78d5664a36c7
$ docker exec vpay-dashboard-probe-run printenv | grep HOSTNAME
HOSTNAME=78d5664a36c7
```

Docker itself injects `HOSTNAME=<container id>` into every container, and
Next's standalone server binds to whatever `HOSTNAME` resolves to — here,
the container's bridge IP (`172.17.0.5`), not `127.0.0.1`. External access
still worked because Docker's port-publish path reaches that same bridge
interface; the internal probe did not. Explicitly setting `HOSTNAME=0.0.0.0`
in the runner stage's `ENV` (matching what the `checkout` stage already
does, for the same unstated reason) fixed it — confirmed by rebuilding and
re-running the exact sequence above, this time green.

**Conclusion: guard 12 (`dashboard-not-templated`) is safe to retire.** The
image starts, runs non-root, refuses writes outside `/tmp`, and answers its
health path — under `--read-only --tmpfs /tmp --user 1000:1000`, exactly the
constraint a Kubernetes `readOnlyRootFilesystem: true` pod imposes. Commit 3
retires it and templates a Deployment.

## What was declined, and why

- **`server.autoscaling.behavior.scaleDown.stabilizationWindowSeconds`
  (60s, above the 35s `terminationGracePeriodSeconds`) has no dedicated
  `_validate.tpl` guard.** The ADR calls it "required, not optional"; this
  branch enforces it only through the default value and documentation. The
  brief's own "three things `just helm-check` will fail you on" section
  scoped the `expected_guards` array change to exactly `+connection-budget,
-dashboard-not-templated`, and adding a fourth guard name was judged
  outside that scope given the remaining time budget. Flagged here rather
  than silently — a maintainer who wants it enforced should add a guard
  comparing it against `terminationGracePeriodSeconds` the way
  `grace-period` already does for the drain deadline itself.
- **README.md's per-key `### Values` tables were not exhaustively updated**
  for every new `management.*`/`server.autoscaling.*`/`dashboard.*` field —
  the object table and guard table (what the brief named explicitly) are.
- **The dashboard's own OAuth wiring** (`dashboard.clientId`/`.redirectUri`/
  `.scope`) is templated as plain, unguarded values. This is a deliberate
  reading of the app's own fail-closed design (a missing value renders a
  "not configured" `/login` page rather than crashing), not an oversight —
  see `values.schema.json`'s `dashboard` description — but it means those
  three values need to be wired up before a dashboard sign-in actually
  works, and nothing here proves they are.
- **No Ingress rule for `/dash/v1`.** The ADR's §5 names only an HTTPRoute
  rule; no Ingress-side equivalent was added, since it was not asked for and
  the dashboard's own BFF reaches `/dash/v1` over the in-cluster Service
  directly rather than through public routing.
- **The companion `vaam-apps/vpay-skills` PR** the ADR's "Documentation and
  status" section asks for was not opened. This branch's own worktree has no
  access to that repository; flagged here per the maintainer's standing
  parity rule rather than silently skipped.

## What this does not prove

No Kubernetes Pod has run any of this. `just helm-check`'s own summary line
says so ("No cluster was involved") and this ADR does not change that —
every probe threshold, every resource number and the two NetworkPolicies are
reasoned from the manifests and from Kubernetes' documented behaviour, not
observed. The Docker-level read-only observation in Commit 2 is real; it is
not a substitute for a Pod, and the ADR's own verification checklist names
that distinction explicitly.

## Remediation, 2026-09-16 — after two adversarial reviews

Two reviews ran against the review head (`42a2ab28`) independently. Seven
findings, R1–R7, remediated below. Every "decisive" claim here is a mutation
that was actually run on this branch and whose failure text is quoted; a
claim with no quoted failure is not one.

### R1 (HIGH) — `/v1/oauth/token` was mounted on a management-only pod

`router` mounted the whole `/v1/oauth` nest whenever **either** surface was
enabled, citing `ADR-0022 § "The partition"`. That section has never
existed (`grep -in 'oauth\|partition' docs/adr/0022-*.md` returned nothing),
and the justification was wrong on the facts as well: ADR-0017's staff grant
terminates at `/dash/v1/oauth/authorize|token`, inside the `dash` nest
(`staff/mod.rs:370`), and `staff/oauth.rs:291` says so — "This endpoint
serves one grant; `/v1/oauth/token` serves the other."

So a `surfaces: [management]` pod served `/v1/oauth/token`: the **merchant**
private-key-JWT grant, minting merchant credentials on the staff tier,
outside ADR-0009's rate limit, which sits in front of the business tier's
copy only.

The nest is now split by route:

| Route                                            | Mints          | `-server` | `-management` |
| ------------------------------------------------ | -------------- | --------- | ------------- |
| `POST /v1/oauth/token`                           | merchant token | yes       | **no**        |
| `GET /v1/oauth/jwks.json`                        | nothing        | yes       | yes           |
| `GET /v1/oauth/.well-known/openid-configuration` | nothing        | yes       | yes           |

The nest itself still mounts on either surface, so an unmounted `/token` gets
the nest's own honest 404 rather than a refusal. The discovery pair stays on
both tiers because the management tier's `resource_auth` validator fetches
JWKS over HTTP: resolving that to the business tier would make a staff
sign-in depend on the business tier being up, which is the coupling ADR-0022
removes.

Neither review's suite could have caught this: `V1_ROUTES` holds no
`/v1/oauth` path at all, because the OP subtree is built by hand precisely

### R2 (HIGH) — the `/dash/v1` route and the management NetworkPolicy could not both be true

With `management.enabled`, `route.enabled` and `networkPolicy.enabled` all
on, the chart published a `/dash/v1` HTTPRoute rule at a Gateway **and**
rendered a `-management` policy whose only traffic-port peer was a bare
`podSelector`. A bare `podSelector` peer matches pods in the policy's own
namespace; a Gateway runs in its own. `helm upgrade` green, every object
healthy, every `/dash/v1` request dropped by the CNI, and the symptom found
by a member of staff who cannot sign in. Neither CI values file rendered both
halves, so the gate could not see it.

**Whether the management tier should face the public gateway is ADR-0022
§ "Left to the maintainer" item 3 and was NOT decided here.** What landed is
the capability plus the forcing function:

1. `networkPolicy.managementIngress.namespaceSelector` — rendered as a
   **second** `from` peer, ORed with the `podSelector` one. Not combined into
   one peer: two selectors inside a single peer are ANDed, and the Gateway's
   pods do not carry the dashboard's labels. `values.schema.json` pinned
   `additionalProperties: false` on that object, so until now an operator
   could not express the admission even having decided to.
2. Guard 24, `networkpolicy-management-route`, fires when all three flags are
   on and `namespaceSelector` is empty. Its message names the symptom, says
   explicitly that the chart is not making the decision, and gives both ways
   out (admit the namespace, or `route.enabled: false`).
3. `ci/values-route-networkpolicy.yaml` — a fourth render, the only one
   producing the `/dash/v1` rule and the `-management` policy together.

`just helm-check` asserts the two **agree** over the rendered YAML. A `fail`
guard can refuse the incoherent combination but cannot assert the coherent
one, so that half is a rendered-YAML check, like the checkout page's.

Rendered peers, from the fourth render:

```yaml
- from:
    - podSelector:
        matchLabels:
          app.kubernetes.io/component: dashboard
          app.kubernetes.io/name: vpay
    - namespaceSelector:
        matchLabels:
          kubernetes.io/metadata.name: traefik
  ports:
    - protocol: TCP
      port: 8080
```

**Decisive, both directions.** Deleting the `{{- with … namespaceSelector }}`
block from `networkpolicy.yaml`:

```

namespace, but the HTTPRoute publishes /dash/v1 at a Gateway in it. Every
/dash/v1 request would be dropped by the CNI with every object reporting
healthy.
```

Emptying `namespaceSelector` in the fourth values file: `helm template` exits
1 naming `guard "networkpolicy-management-route"`. Both reverted.

### R4 (MEDIUM) — the management tier's metrics were scraped by nothing

`deployment-management.yaml` gives the `-management` Service a `metrics` port
and `networkpolicy.yaml` opens the monitoring namespace to it, but
`servicemonitor.yaml` selected `component: server` and `component: worker`

```
vpay-worker     {…, app.kubernetes.io/component: worker}
vpay-management {…, app.kubernetes.io/component: management}
```

**Decisive.** Deleting the third object:

```
helm-check: FAIL — ci/values-full.yaml rendered no ServiceMonitor for
vpay-management; its /metrics port would be scraped by nothing
```

A latent `set -o pipefail` race in `helm-check` surfaced while adding this
and is fixed rather than worked around: `grep -B20 … | grep -q` reports 141

### R6 (MEDIUM) — `connection-budget` was gated in one direction only

ADR-0022's acceptance checklist asks for a fixture in **both** directions.
Only the unset-`maxConnections` direction had one, because `just helm-check`
mapped fixture filename == guard name and a second file for one guard could
not exist. **Not declined — the harness was extended.**

`<guard>.<n>.yaml` variants are now accepted: the suffix is stripped before
the message is checked, so a variant must still fail with its guard's own
name. The distinct-guard count is asserted against the expected list as well
as the per-file loop, so a variant cannot stand in for a missing guard.

`ci/guards/connection-budget.2.yaml` is the arithmetic direction —
(8 + 2 + 1) × 10 = 110 against 100 − 10 = 90. Deliberately plausible numbers:
an 8-replica ceiling against a stock Postgres `max_connections` of 100 is
exactly the release ADR-0022 §3 says works in staging and exhausts the budget
in production.

**Decisive, both ways.** Made to render successfully:
`helm-check: FAIL — fixture 'connection-budget.2' did not fire`. Made to trip
`worker-replicas` instead: `helm-check: FAIL — … failed, but not with guard
'connection-budget'`. Both reverted.
