## Item 1 — the proactive re-mint (`REMINT_AFTER_FRACTION`)

`server/gate.ts`'s `REMINT_AFTER_FRACTION = 0.8` and `staleTokenFor` decide
"replace it"; `server/session.ts`'s `requireStaff` (lines 230–289) acts on
that decision by running `completeAuthorizationCode` — the OAuth
authorization-code leg, session-bound, so a session the OP has deleted or
disabled is refused (`401`, routed to sign-out) rather than handed a
lengthened token. An outage on the mint falls back to the still-valid stale
token; a `401` never does.

**Pure-function proof:** `gate.test.ts`, describe block "replacing the token
before it expires (issue #88 item 1)" — 5 cases (this said "6" until the same
day's review counted them with `--reporter=verbose`), including the decisive
one ("re-mints at the margin, and the token it holds is still good", asserting
`stale-token` **before** the expiry) and the fail-closed direction (absent or
unparseable expiry reads `stale-token`, not `ready`).

**Real-browser proof:** `dashboard.cy.ts`, "replaces the access token before
it expires, so a long session never sees a 401" — under
`compose.e2e.yml`'s 30 s `demo_staff_token_ttl`, it reads
`access_token_expires_at` from vpay itself, waits to 85 % of the token's life,
re-visits, and asserts the expiry **moved** while the old one had not yet
passed — then waits past the original expiry entirely and asserts the page
still renders with no sign-in. This is the case that tells the proactive
re-mint apart from the pre-existing reactive retry in `dash-read.ts`.

Not separately re-run here (it needs the full `compose.e2e.yml` stack, which
`just test-e2e` — forbidden to this pass — brings up); the "refuses everything
again after signing out" and paging legs of the same spec did run today, see
item 3.

## Item 2 — outage tolerance (keep the cookie on anything but a 401)

`refusalFor` (`server/gate.ts`) and `dashAuthProvider.onError`
(`dash/auth-provider.ts`) both map exactly `401` to `sign-out`; every other
status — `400`, `403`, `404`, `409`, `429`, `500`, `502`, `503`, and no
status at all (a rejected `fetch`) — maps to `outage`, which keeps the
cookie and renders the failure with its request id. `totpGateFor` carries the
same rule on `/login/totp`'s stage read (the exp36 review's finding F6).
`requireStaff` (`session.ts` lines 217–226) and `checkSession` both call
`refusalFor` rather than reimplementing the rule or falling back to
`alreadySignedIn()`, which answers `false` for an outage too and would sign
everyone out of a rolling deploy.

**Proof, run in this pass:** `gate.test.ts` (`refusalFor`, `totpGateFor`) and
`auth-provider.test.ts` (`onError`, structural `isSignOut`) — see output
below.

**Real-browser proof, already on record today:**
[2026-09-12-dashboard-refine.md](2026-09-12-dashboard-refine.md) names issue
#88 item 2 by number for `onError`'s mutation table (9/15 and 10/15 failed on
the two named widenings) and its "Correction, same day" section records a

## Item 3 — the end-to-end paging test

`dashboard.cy.ts`, "pages forward and back through a list, returning the same
rows in both directions" (landed in #130, fixed the same day of a
green-theatre bug: the first version only clicked "Next" when a link already
existed and so never once exercised a second page). As it stands today it:

1. mints 30 extra PaymentIntents via the `mintPaymentIntentsForPaging` task
   so a second page is not optional,
2. records the first page's row IDs, asserts a "Next" link **exists**
   (unconditionally) and clicks it,
3. asserts the second page's rows do not overlap the first,
4. asserts a "Previous" link **exists** on the second page (unconditionally)
   and clicks it,
5. asserts the resulting rows equal the first page's, in the same order.

**That paragraph originally continued: "That ties _both_ ends of the backward
`has_more` inversion … if `hasNewer`/`hasOlder` were swapped, step 2's `Next`
assertion or step 4's `Previous` assertion breaks — this is not asserted from
reading the code, it was run, see below." Not one part of that survives,
and the same day's adversarial review measured why.** Steps 2 and 4 do not
break under the mutation, so the case tied neither end; and "it was run"
attached the mutation below — which ran against `payments-query.test.ts` — to
a sentence about steps 2 and 4, which nothing ran. The mutation changes only the `pagingBackwards`
branch, and the five steps above read a pager on a forward page twice and
never on a backward one. Evaluated over the three states this case actually
walks (33 rows on the tenant, `PAGE_SIZE` 25):

| Page                      | shipped rule           | mutated                |
| ------------------------- | ---------------------- | ---------------------- |
| first (no cursor)         | prev — , next `after=` | prev — , next `after=` |
| second (`after=`)         | prev `before=`, next — | prev `before=`, next — |
| back to first (`before=`) | prev — , next `after=` | prev `before=`, next — |

Step 2 sees a Next either way, step 4 sees a Previous either way, and step 5
compares row IDs, which the mutation does not move. **As it stood, this case
was green against the defect it was written for.**

**Repaired the same day, in the case rather than in this log.** After the
Previous click it now asserts the backward page's own pager —
`nav[aria-label="Payments paging"] a[rel="next"]` exists and `a[rel="prev"]`
does not — which is the one row of that table the mutation changes, and it
changes both of its cells. `rel` rather than link text, so a payment id
containing "next" cannot satisfy it. With that, the round trip ties both ends.
It still does **not** separately test a _third_ page's continuation past the
second.

**Decisive mutation, run and reverted in this pass** (`payments-query.ts` is
not one of the five files this pass was told to leave alone):

```
const hasNewer = pagingBackwards ? hasMore : !onFirstPage;   // was
const hasOlder = pagingBackwards ? true : hasMore;            // was
        ↓
const hasNewer = pagingBackwards ? true : !onFirstPage;       // mutated
const hasOlder = pagingBackwards ? hasMore : hasMore;          // mutated
```

`payments-query.test.ts` went from 14/14 to **12 passing, 2 failing** — both
failures in "paging backwards, where has_more means the opposite thing", the
exact block this exists to catch. Reverted; 14/14 again (`git diff` clean
afterwards — confirmed below).

**What is still not run, stated plainly:** this same mutation against the
live `dashboard.cy.ts` case itself. `status-read-seam-and-bff.md` named that
gap on 2026-09-11 ("neither has the decisive mutation... been run") and it is
still true at that exact level — what has changed since is that the _un_-
mutated case has now run green against a real stack
(`2026-09-12-dashboard-refine.md`, 17/17), where on 2026-09-11 it had not run
at all. The unit-level mutation above is a different, narrower layer of proof
than "break `pageCursors`, watch this Cypress case go red" — it shows the
function the test depends on is correctly guarded, not that the Cypress
assertions themselves are wired to it end to end. Nobody should read this
log as having closed that residual.

**Sharpened by the review, same day:** that residual was understated, not
