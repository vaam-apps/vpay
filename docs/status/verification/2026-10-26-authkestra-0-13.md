# 2026-10-26 — authkestra `=0.7.1` → `=0.13.1`, and RUSTSEC-2026-0387 stays accepted

## What this is

The four authkestra crates (`authkestra-op`, `authkestra-engine`,
`authkestra-resource`, `authkestra-axum`) move from `=0.7.1` to `=0.13.1`, the
newest release on crates.io on 2026-10-26 (`cargo search authkestra-op`). The
maintainer asked for it twice: "Accept, and upgrade authkestra" on 2026-10-24,
and "Upgrade authkestra and accept the advisory" on 2026-10-26.

**The upgrade does not clear RUSTSEC-2026-0387.** It moves the chain and leaves
the advisory where it was. The `deny.toml` entry stays, with its reasoning
re-checked at 0.13.1.

## The advisory, at 0.13.1

`cargo tree -i crypto-bigint@0.5.5 -e normal`, after the bump:

```text
crypto-bigint 0.5.5 <- elliptic-curve 0.13.8 <- ecdsa 0.16.9
    <- p256 0.13.2 / p384 0.13.1 <- jsonwebtoken 11.0.0
    <- authkestra-engine / authkestra-op / authkestra-resource 0.13.1, vpay-sdk
```

The fix is in `crypto-bigint` 0.7.6, which needs `elliptic-curve` 0.14.
`jsonwebtoken` 11.1.0 is still its newest release on 2026-10-26
(`cargo search jsonwebtoken`), and it still requires `p256 ^0.13`. authkestra
0.13.1 still requires `jsonwebtoken` 11, with the `rust_crypto` backend. No
version of anything in the chain clears it today.

The acceptance rests on vpay never signing with an EC key. Re-read at 0.13.1:

- authkestra signs with an EC key only inside `#[cfg(test)]` modules. In
  `authkestra-engine`'s `token/dpop.rs`, a P-256 `SigningKey::random` at line
  874 sits inside the `#[cfg(test)]` module that opens at line 415. In
  `authkestra-op`'s `handlers/enrolment.rs`, the one at line 425 sits inside
  the module that opens at line 351.
- The OP signs RS256. Merchant webhooks use HMAC. The remaining keys are
  Ed25519, which is `curve25519-dalek`, not `crypto-bigint`.
- **New in this re-read:** `vpay-sdk` links `jsonwebtoken` too, and signs
  only RS256. `sdks/rust/src/auth.rs` builds `Header::new(Algorithm::RS256)`,
  and `Credentials` accepts an RSA PEM and nothing else.

This is a reading of the call sites, not a timing measurement, as it was on
2026-10-24.

## What authkestra changed that vpay had to follow

Each item below was a compile error at 0.13.1. Each fix is the smallest one
that keeps vpay's behaviour.

| Upstream change                                                                                                                                     | Since   | vpay's change                                                                                                                                                                                                                         |
| --------------------------------------------------------------------------------------------------------------------------------------------------- | ------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Store traits moved to `authkestra_engine::store::traits`, take `&mut self`, and return `authkestra_engine::store::StoreError` instead of `OpError`  | 0.8     | Every vpay store impl: `vpay_db::client_assertion`, `vpay_api::op::{clients, dashboard, refusing_stores}`. `vpay-db` gains a direct `authkestra-engine` edge, because `authkestra-op` does not re-export `StoreError`. No new package |
| Handlers take `&mut dyn OpStore`. The axum adapter gets a per-request store from `CloneableOpStore::clone_op_store()`, and a clone must share state | 0.8     | `MerchantOp` and the dashboard OP hand out a fresh boxed store per request. `DashboardClientStore` and `PgAuthorizationCodeStore` derive `Clone` over a shared `PgPool`, so clones share state, as the trait requires                 |
| `AuthorizeOutcome` is `#[non_exhaustive]` and gained `ReauthenticationRequired`, which fires only on `max_age` or `prompt=login`                    | 0.11    | `staff::oauth::authorize` gains a wildcard arm that logs and refuses **without redirecting**. `AuthorizeQuery` forwards neither parameter, so the arm is unreachable today                                                            |
| `Jwk` is `#[non_exhaustive]`                                                                                                                        | > 0.7.1 | One test fixture in `resource_auth.rs` builds its JWK with `Jwk::rsa(n, e).with_kid(..).with_alg("RS256")`                                                                                                                            |
| `authkestra-engine`'s `session` and `token` features are gone. Token machinery always compiles in                                                   | 0.11    | The workspace's engine features are `["rustls-no-provider"]` only                                                                                                                                                                     |

One message changed, on a path nothing reaches. The refusing stores used to
hand back `OpError::GrantTypeNotPermitted`. `StoreError` has no such variant,
so they now return `StoreError::Internal` carrying the vpay error's `Display`.
The grant handlers turn **any** store error into `server_error` without
inspecting it, at 0.7.1 and at 0.13.1, so the HTTP answer is unchanged.

## What was re-read and found unchanged

Read in the extracted crate sources, at 0.7.1 and 0.13.1 side by side:

- `verify_client_assertion`. The `Validation`, the 60 s leeway comment (line 400) and the 300 s `exp` ceiling (line 436) are as they were. Only the
  `ClientAssertionStore` trait it calls changed shape, and the trait's
  definition moved to the engine. `client_assertion.rs` differs by 112 diff
  lines, all about the store trait and the in-memory store.
- `mint_client_assertion` (engine). Byte-identical. `vpay-sdk`'s port of it
  cites it.
- `assertion_algorithms`. Byte-identical.
- `handle_client_credentials`. It still takes no `op_store`, so `/v1`'s one
  grant cannot reach a store.
- The audience default for a token request with no `audience` is still the
  `client_id` (`handlers/token.rs:1316`).
- Step 7 of `default_handle_authorization_code`. It still mints with
  `Some(client_id)` as the audience, with no requested-audience path.
- `handle_token`. It still passes `None` for both the mTLS certificate and
  the DPoP header.
- `authkestra-axum`'s `axum_token_handler` tail, which
  `docs/reference/vpay-api/merchant-op.md` inlines. Identical at lines
  271–278.
- `authkestra-resource`'s `JwksCache` refresh policy. `JwksCache::new` still
  builds a `reqwest::Client` eagerly, so the reason for `vpay_api::jwks_cache`
  being a port still holds. `ValidationError` has the same variants.

Two upstream changes reach vpay's behaviour, both narrowly:

- **`Jwks::find_key` skips a key that is not published for signature
  verification** (0.10, authkestra#342): a key whose `use` is set and is not
  `sig`, or whose `key_ops` is set and lacks `verify`. A key with neither
  field set is still usable. `vpay_api::jwks_cache` calls `find_key`, so it
  inherits this.
- **A loopback redirect URI matches on any port** (0.7.2, authkestra#307,
  RFC 8252 §7.3). This applies only to `http` URIs whose host is the IP
  literal `127.0.0.1` or `::1`, never `localhost`, and only when the
  registered URI is one too. A dashboard `redirect_uris` entry of that shape
  now accepts any port. `validate_host` already refuses a plain-`http` host
  in livemode.

## Lockfile

New packages: `argon2` 0.6.0, `password-hash` 0.6.1, `phc` 0.6.1, `blake2`
0.11.0, `sha1_smol` 1.0.1. `argon2` 0.6.0 is the engine's. vpay's own staff
hashing stays on 0.5.3, so the lock carries both. `deny.toml`'s
`multiple-versions = "warn"` reports that duplicate without failing.

## Not done

- **vpay's staff password hashing stays on `argon2` 0.5.3.** Moving it to 0.6
  is its own change, with a test that hashes already stored still verify.
- **The `authkestra.*` tables are left in place.** Nothing reads or writes
  them, and has not since 2026-09-05. Dropping them needs a migration and the
  maintainer's decision, as `backend.md` has said since then.
- **No new authkestra feature is wired.** That includes DPoP, `max_age` and
  `prompt` on the dashboard authorize request, magic links, one-time codes,
  recovery codes, Cedar policy and SSF.
