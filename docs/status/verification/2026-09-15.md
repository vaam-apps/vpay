# 2026-09-15 — The first real rail call (live MTN sandbox test)

## What happened

On 2026-09-15 the `live` profile
(`config/application-live.yml`, untracked local file) was run against **MTN's
real sandbox** for the first time, and a payment settled. This page records
what was observed and what was run, and is deliberately **not** a `just ci`
page: full `just ci` / `just verify` have not been run on this branch.

Stack: `vpay-server` (`--profile live`) + `vpay-server worker` on the host,
against the repo's own `vpay-pg` Postgres (`localhost:5433`, user/db `vpay`),
with real sandbox credentials sourced from a git-ignored `.env.live`
(`MTN_SUBSCRIPTION_KEY` / `MTN_API_USER` / `MTN_API_KEY`).

Driver: `.e2e/live-sandbox-driver.mjs` (git-ignored), which mints a
`client_credentials` token as `live-merchant`, creates a EUR `mtn_momo`
PaymentIntent, confirms it with the MTN-sandbox test MSISDN `46733123454`, and
polls `GET /v1/payment_intents/{id}` until the worker settles it.

Observed (from the driver and the worker log):

1. `POST /v1/payment_intents` → `pi_xxd2xj1e914e16c6m63gezag`,
   `requires_payment_method`.
2. `POST …/confirm` with `payment_method_data.type = mtn_momo` → `processing`.
3. Worker polled; at 12:13:04 UTC it logged
   `the rail reported a charge as paid` (`charge_id=ch_djfmqmck853ps9qh845vd825`).
4. Driver poll showed the intent reach `succeeded` ~60 s after confirm.

Merchant authentication (`private_key_jwt` → bearer token) worked end-to-end
against the running server, as it did in the prior session.

## Two real bugs found by this run, and fixed on this branch

Neither could be caught by the WireMock suite, because the stub accepted the
request the adapter actually sent.

1. **The token mint posted no body.** `vpay-adapter-mtn-momo::token::mint`
   sent `POST /collection/token/` with headers only; MTN's gateway answered
   `411 Length Required`. Reproduced with curl: no body → 411.
   Fixed to send `{"grant_type":"client_credentials"}` with
   `Content-Type: application/json`.
2. **The JSON spelling is mandatory, not incidental.** When the same grant was
   then sent form-encoded (`grant_type=client_credentials`, the spelling
   `vpay-adapter-orange-money` uses), MTN's gateway answered a 200 "Request
   Rejected" HTML page instead of JSON. Reproduced with curl over HTTP/1.1 and
   HTTP/2, canonical and lowercase header casing: only the JSON body returns a
   token. An HTTP/2-only theory was tested, disproven (HTTP/2 + JSON works),
   and the ALPN change made under that theory was reverted.

Both reproductions used the real sandbox credentials from `.env.live`; no token
value was printed to any log or this page.

## What was run on this branch

- `cargo test -p vpay-adapter-mtn-momo` — 62 unit tests + 1 doctest, all pass.
- `cargo test -p vpay-provider -p vpay-sdk` — all pass (the ALPN revert is
  byte-identical to master for these crates).
- `cargo nextest run -p vpay-tests-conformance` — 54/54 pass, **with the MTN
  token stub tightened to require the JSON body** so a bodyless or
  form-encoded mint can never go green again.
- The live sandbox payment above (three runs total: the first found bug 1, the
  second found bug 2, the third settled).

Not run on this branch: full `just ci` / `just verify`, `just test-web`,
`helm-check`, `just audit-web`. The adapted crates and the conformance suite
are green; the workspace-wide gates on `master` were green at the last
recorded `just ci` and nothing in this change touches the frontend, the schema
or the migrations.
