### A third false green — and CI, not this machine, is what caught it

**The first push of this branch failed CI's `web` job, and it was right to.**
`just test-storybook` had been run green on this machine several times, exit
0, 93/93. On a GitHub runner the same command reported **"93 passed" with 24
unhandled errors** and exit 1: `TypeError: Cannot read properties of null
(reading 'useContext')`, thrown out of vite's pre-bundled
`@base-ui/react/{select,button,radio-group}`.

Two things about that are worth keeping.

**A story that throws while rendering still counts as a passing test.** The
24 stories that died never had axe run on them at all, and the line vitest
printed was `Tests 93 passed (93)`. Only the separate `Errors` count and the
exit code said otherwise. A green test count is not evidence that a story
rendered.

**It reproduces only from a cold dependency cache**, which is why this
machine kept passing and a fresh runner did not: vite discovers
`@base-ui/react`'s subpath entries mid-run, re-bundles, and modules loaded
before the re-bundle keep a `null` React. Cleared locally, it reproduced
immediately — 34 errors.

Fixed by declaring every dependency the stories reach in
`optimizeDeps.include`, so nothing is discovered after the first story
renders. Two other fixes were tried and measured first, and neither worked:
`resolve.dedupe: ["react", "react-dom"]` alone left 36 errors, and
`optimizeDeps.exclude: ["@base-ui/react"]` made it worse — 8 test files
failing outright with React `null` at `useRef`, because React is CJS and
excluding it from pre-bundling is what breaks the import.

Verified after the fix: **three consecutive cold-cache runs, 30 files / 93
tests / 0 errors / exit 0 each**, and a cold-cache mutation run (the `todo`
removed from `text.stories.tsx > Tones`) still failing on the 2.92:1
contrast violation with **zero** unhandled errors — so the fix did not
paper over the defect by suppressing rendering.

`just test-storybook` now clears `node_modules/.cache/storybook` before every
run. Ten seconds, so that the recipe means the same thing on a developer's
machine as it does on a cold runner.

AA wants 4.5:1 for body text. The first three are one cause — bumblebee's
`--color-error` used as a **foreground** on `--color-base-100`, a pair nothing
in this repository had ever measured: `theme-contrast.test.ts` and
`outcome-contrast.test.ts` both pin `--color-error` as a _background_, beneath
`--color-error-content`, which is the pair the 2026-09-07 review corrected.

**The theme was proved applied rather than assumed.** axe reported the
foreground as `#ff6266`; the repo's own `oklchToLinearRgb(0.70, 0.191,
22.216)` — bumblebee's `--color-error` as `styles.css` declares it — returns
exactly `#ff6266`. If the decorator had not run, the browser would have
painted a different palette and the number would not match.

All four carried `a11y: { test: "todo" }` for a few hours. **They are fixed
now**, and `DECLARED_TODOS` in `src/testing/a11y-gate.test.ts` is empty.

### The fix

daisyUI has no ink for text on a light surface — `--color-<tone>` is a
**fill**, the colour a filled component paints as a background. `styles.css`
adds the two that were missing:

| Token               | Value                                | on `base-100` | on `base-200` |
| ------------------- | ------------------------------------ | ------------- | ------------- |
| `--color-error-ink` | `oklch(55% .191 22.216)` = `#c92d3a` | **5.36:1**    | **4.91:1**    |
| `--color-muted-ink` | `oklch(48% 0 0)` = `#5d5d5d`         | **6.54:1**    | **5.99:1**    |

`--color-error-ink` keeps daisyUI's own hue and chroma and is darkened only as
far as AA needs plus a margin — the same rule the 2026-09-07
`--color-error-content` correction used. `oklch(58%)` is nearer the original
red and clears by 0.22, which is too thin to spend on a payment failure;
`oklch(52%)` is 6.09:1 and reads brown. Both candidates were measured, not
guessed.

**`--color-error` is unchanged.** Every alert, badge, button and input border
keeps the colour it has, and every pair `theme-contrast.test.ts` and the
checkout's `outcome-contrast.test.ts` already pinned still holds — this fix
adds a pair rather than moving one.

**The muted half was a compounding bug, not a too-light colour.** `List` set
`opacity-70` and `Text tone="muted"` set `opacity-60`. Each is defensible
alone — 6.70:1 and 4.73:1 — but they multiply, so a muted line inside a list
rendered at 0.42: `#9d9d9d`, **2.71:1**, and nothing at either call site could
show you that. Colour does not compound. `#5d5d5d` is one sRGB step from what
`opacity-70` already painted, so a list looks as it did and two of them nested
now produce one colour instead of a third. Five call sites moved in total:
`Text`'s `muted` and `error` tones, `FieldError`, `FieldDescription`,
`DialogDescription` and `List`. `opacity-[0-9]` no longer appears in any
component source.

**The model was validated before anything was changed**: a linear-space blend
disagreed with axe, an sRGB-space one reproduced `opacity-42 → #9d9d9d →
2.71:1` exactly — the number axe reported from the browser.

### What keeps the fix

`src/theme-ink-contrast.test.ts` measures both inks on both surfaces from the
compiled stylesheet, so the fix holds without a browser. It also fails if a
component writes `text-error` or any `opacity-*` again, and it asserts
`--color-error` is **still** unreadable on white — so a daisyUI bump that
fixes it upstream retires these tokens rather than leaving them carried out of
habit.

It is a separate file because `just verify-ui` caps a file in this package at
200 lines; adding the cases to `theme-contrast.test.ts` took it to 252 and the
gate refused it. That refusal is in this branch's history rather than smoothed
away, as is a first-draft assertion that used `/\btext-error\b/` and passed
for the wrong reason — `-` is a word boundary, so it matches inside
`text-error-ink`. It compares class **tokens** now.

Four mutations against it, all caught, all reverted: `error-ink` lightened to
`oklch(65%)` (2 failed), `muted-ink` to `oklch(62%)` (2 failed), a component
back to `text-error` (1 failed), a component back to `opacity-60` (1 failed).
