## The styling gate

`just ci` builds neither web app, so nothing in this repository's automated
gates had ever compiled either app's real `globals.css` and inspected the
output — the exact failure mode the packages' own READMEs warn is silent: a
missing `@source` line or a dropped `themes: false` renders every
`@vaam-apps/ui` component unstyled, or the wrong theme, with no error and no
warning anywhere.

One vitest file per app
(`frontends/apps/{dashboard,checkout}/src/styling-gate.test.ts`), each
compiling the app's real `app/globals.css` through
`postcss([tailwind()]).process(...)` — the same mechanism
`<SCRATCHPAD>/dashui-measured-facts.md` §5 measured runs under plain Node —
and asserting two things: (a) a utility class only `@vaam-apps/ui`'s
compiled `dist` writes is present in the output, and (b) `--color-base-100`
resolves to the theme's `#0a0b0d` and to nothing else.

**A real defect was found and fixed while building this gate, not after.**
The first draft spelled the candidate class (`text-subtle-foreground`)
literally in the test file's own doc comment, to explain what it was
checking for. Tailwind v4's content scanner has no notion of "prose" versus
"a real render" — it extracts class-shaped tokens from any text file it
reaches and treats a match as usage. **Measured directly:** with the
`@source` line deleted from `app/globals.css`, a sibling `.ts` file merely
mentioning the class name in a comment was sufficient, on its own, to make
Tailwind regenerate the utility — the case would have passed whether or not
the gate it claims to check actually held. Fixed by building the candidate
string from parts at runtime (`["text", "subtle", "fore" + "ground"].join("-")`)
so the literal contiguous token never appears in either app's `src/`. Both
mutations were then re-run against the corrected test file and did fail
correctly:

| App       | Baseline         | `@source` line deleted               | `themes: false` removed                                                                                       |
| --------- | ---------------- | ------------------------------------ | ------------------------------------------------------------------------------------------------------------- |
| dashboard | exit 0, 2 passed | **exit 1** — candidate class count 0 | **exit 1** — `--color-base-100` resolves to `#0a0b0d`, `oklch(100% 0 0)` **and** `oklch(25.33% 0.016 252.42)` |
| checkout  | exit 0, 2 passed | **exit 1** — candidate class count 0 | **exit 1** — same three values                                                                                |

Both mutations were reverted after being observed to fail; `git diff` was
checked empty against a saved backup after each revert.

The same real-build assertions were then re-checked on both apps' actual
`next build` output (`.next/static/css/*.css`), belt and braces:

| App       | `text-subtle-foreground` present | `--color-base-100` values |
| --------- | -------------------------------- | ------------------------- |
| dashboard | yes                              | `#0a0b0d` only            |
| checkout  | yes                              | `#0a0b0d` only            |

The checkout keeps its own runtime brand-colour retargeting on top of this
(`src/config/theme.ts`, decision 3) — `src/config/theme.test.ts`'s 31 cases,
including all six WCAG AA "clears contrast against the computed foreground"
cases, pass unchanged against the new dark ground.

### `pnpm install` — the decisive one, and what it actually found

**First attempt: `ERR_PNPM_PEER_DEP_ISSUES`.** Not a `@vpay/ui` remnant —
`@testing-library/jest-dom@6.10.0` and `@testing-library/react@16.3.2` both
declare a peer on `@testing-library/dom`, which **no `package.json` in this
workspace has ever declared directly**. It was reaching every consumer only
transitively, through `frontends/packages/ui`'s own Storybook devDependency
chain (`@storybook/react-vite` and friends) — confirmed by diffing the
lockfile at `HEAD` against this branch: `HEAD`'s lockfile resolves
`@testing-library/dom@10.4.1` as an actual installed package; this branch's,
before the fix, resolves it nowhere at all, only as an unmet peer
declaration. Deleting the one workspace member that incidentally supplied it
exposed a dependency three packages had always needed and never declared.

**Fixed by declaring it explicitly**: `@testing-library/dom: ^10.4.1` added
to `devDependencies` in `frontends/apps/checkout/package.json`,
`frontends/apps/dashboard/package.json` **and** `examples/shop/package.json`
— the third because the same transitive supply, and the same exposure, hit
it too, even though it never depended on `@vpay/ui` at all.

**Re-verified from a genuinely clean state, not just a green re-run**: every
top-level `node_modules` in the workspace was removed and
`pnpm install --frozen-lockfile` run again. **Exit 0**, 684 packages linked,
no peer warning. `@testing-library/dom@10.4.1` now resolves as an actual
package for all three affected importers (confirmed by grepping the
regenerated lockfile).

`pnpm-lock.yaml` diff: **1 404 lines removed, 71 added** — dominated by
`frontends/packages/ui`'s own dependency subtree (Storybook and its
addons chief among it) leaving the graph.

## Integration findings — the seams this group exists to catch

Groups B, C, D and E worked in parallel and, correctly per the plan, never
ran the full integrated gate against each other's landed work. This group
was the first to run `just verify-ui`, `pnpm -r lint` and `pnpm -r typecheck`
against the complete tree, and it was not clean on the first pass:

1. **`screens.tsx:569`** (Group D) — `className={problem === null ? undefined : "input-error"}`
   on the MSISDN `<Input>`: a computed `className`, which check 7a-i refuses,
   _and_ `input-error` is itself a banned daisyUI component class (check
   7b) — `@vaam-apps/ui`'s `Input` has no error/invalid variant at all
   (verified `input.js`: `className` and passthrough props only, no
   `tone`). Fixed by dropping the attempted border-colour change entirely;
   `aria-invalid` still carries the state for assistive technology, and the
   adjacent error text is the payer-visible signal. Named as a real,
   unabsorbed regression in the file's own header, not worked around.
2. **`screens.tsx:588`** (Group D) — `className="text-caption text-state-danger-fg"`
   on the same field's error text: a literal status-colour token, which
   check 7a-ii refuses (`AGENTS.md`: "never inline a status colour in a
   component"). Fixed by moving the identifying attributes (`id`, `role`,
   `data-testid`) onto a plain wrapping `<div>` and painting the colour with
   `InlineBanner variant="danger"` nested inside it — the same pairing
   `ReadyRedirect` already used a few dozen lines above. A second, unrelated
   instance of the identical `InlineBanner`/`data-testid` mistake was found
   and fixed in the same file while there (`ReadyRedirect`'s own
   `data-testid="redirect-problem"` had been passed directly to
   `InlineBanner`, which forwards neither `id` nor `data-testid` — silently
   dropped, untested, harmless only because nothing queried it).
3. **`locale-switch.tsx:65`** (Group D, decision 8) — `className="select select-sm"`,
   a legitimate, forced use of daisyUI's own classes (`@vaam-apps/ui` has no
   labelable `Select`), refused by check 7b's blanket ban. Not a defect —
   `verify-ui` (Group E) and the forced native `<select>` (Group D,
   decision 8) were each correct in isolation and incompatible together.
   Fixed with one narrow, named, dated exemption in check 7b-ii, scoped to
   this exact file rather than to `frontends/apps` generally, with the
   reasoning recorded beside it in the recipe.
4. **`frontends/packages/config/src/eslint.test.js:227`** — a fixture array
   (`it("react-hooks is on in the React packages", ...)`) hard-coded
   `frontends/packages/ui/src/components/status-badge.tsx` as one of four
   paths. `PACKAGE_DIRS` is derived live from `git ls-files -- '*/package.json'`,
   so once that package's `package.json` was gone, `rulesFor` threw
   `TypeError: The "path" argument must be of type string. Received
undefined` — **confirmed by running the suite**: 59 passed, 1 failed,
   exactly this case. Fixed by removing the deleted package's entry; the
   three remaining paths (checkout, `examples/shop`, dashboard) are every
   `react: true` package left in the workspace, so there was no fourth to
   substitute. **60 passed, 0 failed** after the fix.
5. **`screens.tsx:162`** — an ESLint `--fix` for an unrelated
   `no-unnecessary-type-assertion` finding (see below) initially deleted a
   type-widening cast whose purpose was invisible to the rule locally;
   caught by re-running `tsc --noEmit` immediately after the autofix rather
   than trusting the lint run alone.

**Mechanical lint findings, all real, all pre-existing (surfaced by the same
first full-tree run), fixed and re-verified:**

- `checkout-view.test.tsx:594,644` and `screens.tsx:162`:
  `@typescript-eslint/no-unnecessary-type-assertion`. The first two were
  genuinely redundant `as HTMLSelectElement` casts, safely auto-fixed. The
  third (`VaamCheckboxField as unknown as (...)`) was NOT safe to
  auto-remove: the assignment statement itself needed no cast, but removing
  it broke every JSX call site passing `as`/`type`/`data-testid` — TypeScript's
  excess-property check on those call sites then failed
  (`tsc --noEmit`: `Property 'as' does not exist on type
'…CheckboxFieldProps'`). Fixed by replacing the assertion with an explicit
  variable type **annotation** carrying the same widened shape — annotations
  aren't `as`/angle-bracket assertions, so the rule has nothing to flag, and
  the downstream call sites keep type-checking.
- `screens.tsx:323,330` and `app/login/page.tsx:45`:
  `better-tailwindcss/enforce-consistent-class-order` — pure token
  reordering, auto-fixed, re-verified against both apps' full test suites
  (no behaviour change; confirmed by an unchanged pass count on each).
