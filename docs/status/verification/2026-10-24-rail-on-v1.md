# 2026-10-24 — the rail on `/v1`: `payment_method_details` on the intent

Branch `claude/happy-hopper-r3h6rz-rail-on-v1`, from `master` at `98f4d32b`
(vaam-apps/vpay#363's merge, whose sentences this one edits). The change was
written and gated on #363's head `87e29530`, whose tree is identical to
`98f4d32b` (`git diff` is empty), and then moved onto it. Every `payment_intent` now carries
`payment_method_details`, `null` until it has a charge and then
`{type, rail}`, from two columns migration `0054` adds to `payment_intents`.
Proven by unit tests run here; the database-backed and integration cases were
written and compiled and **could not run in this environment** (§ "What was
not run"). **No rail was called.**

## Whose decision

- **The maintainer's**, on 2026-10-24. "Both" on routed refunds, the first
  half being [2026-10-24-refund-by-method-type.md](2026-10-24-refund-by-method-type.md).
  Then, offered three shapes for the second half
  ([../../plans/2026-10-24-rail-on-v1.md](../../plans/2026-10-24-rail-on-v1.md)),
  **"Go with A"**: the key on the intent. The plan's three other defaults
  stand:
  - ADR-0029 D10 is amended so the outcome is on `/v1` and the decision
    record is not;
  - the payer's browser surface renders the same object;
  - past `events.data` is never rewritten.
- **The implementer's, each reversible and named here:**
  - **the copy is written inside `vpay_db::charges::insert_for_intent`**, not
    by each caller. Every charge vpay opens goes through it, so the pair
    cannot be forgotten;
  - **the backfill copies the charge's `method_type` exactly**, `NULL` for a
    charge written before `0053` even on a single-type rail. The plan's draft
    said such a charge would be typed by rule. That was corrected before
    building: it would make the intent say something its charge does not;
  - **`type` is validated through `vpay_core::routing::MethodType`** at render
    time. A stored value outside it, or a type without a rail, is
    `ApiError::Internal`, never rendered;
  - **`model PaymentIntent` is not extended**, for `0053`'s reason: no query
    on the table runs through CrateStack.

## What changed

- **Migration `0054_payment-intents-charge-rail.sql`:**
  - `charge_rail` (`REFERENCES providers (code)`, as `charges.provider_code`
    is) and `charge_method_type`, with `charge_method_type_is_known` (the same
    two spellings as `charges.method_type`) and
    `charge_method_type_needs_a_rail`;
  - the backfill;
  - a `COMMENT ON` each column;
  - a corrected `COMMENT ON TABLE routing_decisions`, whose "Never on the /v1
    object" now names what is on it.

  `MANIFEST.sha256` gained the line from `just migrations-manifest`, and the
  migrations README its count, 53 → 54.

- **`vpay-db`:**
  - `RECORD_CHARGE_ON_INTENT`, `UPDATE payment_intents SET charge_rail = $2,
charge_method_type = $3, updated_at = now() WHERE id = $1 AND charge_rail
IS NULL`, run by `insert_for_intent` after its `INSERT`, from the
    returned row. Zero rows is `DbError::WriteMatchedNoRow`;
  - `PaymentIntentRow` gains both fields, in `COLUMNS` and in its `Debug`.

  - a stripe-compat case;
  - Flutter is not changed (§ "Not done").
- **Schemas:** both columns in `schemas/privacy-inventory.yaml`'s

- **Docs:** `docs/api/README.md`, ADR-0029 (D10 and its Status), both plans,

### CI's first two runs (2026-10-24)

CI's first run on `bdee8ce3` (run 40088117080) passed `web`, `e2e (compose)`,
the stripe-compat case, every self-check and the scans. Its `rust` job did
not finish:
`vpay-db::repositories a_cancel_racing_a_settlement_leaves_one_terminal_state_and_one_event`
was still running when the job was cancelled after 1 h 55 min. 1 779 of
2 489 tests had passed; none had failed, and nothing passed after it hung.

The test held a cancel's transaction open, so it held the intent's row lock,
and then committed a charge synchronously on another connection before
releasing the cancel. Its own comment gave the reason that was safe: "a charge
insert does not touch `payment_intents`". This change makes that false.
`insert_for_intent` now writes the intent's row, so the insert waited for the
cancel, and the cancel waited for the test. That is a deadlock Postgres cannot
see.

In shipping code it is not a deadlock. A real cancel commits on its own, so a
confirm racing it now waits for the cancel and then commits its charge onto
the `canceled` intent (its `charge_rail IS NULL` guard still matches). The
settlement's status guard then refuses that charge loudly, as before. The
test now opens the charge in a task and asserts that it **waits** for 750 ms
while the cancel holds the row. It then releases the cancel and asserts the
same outcome as before: the settlement fails with `WriteMatchedNoRow` on
`payment_intents`, there is one `payment_intent.canceled` event, and the
charge stays `submitted`. That wait is also the first database-backed check
that opening a charge writes the intent at all.

The second run, on `feeba837` (run 40096632810), ran 2 333 of 2 489 tests:
2 332 passed and one failed. `postgres_smoke`'s
`the_cstack_schema_drifts_from_the_migrations_by_a_measured_amount` measured
the drift at exactly the predicted 212 over 28. It failed on its other
assertion, the list of multi-column CHECKs read from `pg_constraint`, which
the report cannot see: `payment_intents.charge_method_type_needs_a_rail` was
live and not in the list. It is in the list now. nextest stops at the first
failure, so the last 156 tests are measured by the run on the head that adds
it.

  before `0053`, keeps `type: null`. vpay never recorded the network.
