## The headline, first

**Nothing in this merge moved a refund closer to paying a payer, and nothing in
it may be read as "refunds work".** All five `/v1` refund routes are mounted.
No refund has ever moved money: `mtn_momo::refund` is MTN's Disbursements
`transfer` and is WireMock-proven and rail-unproven — MTN's Disbursements
product has never been called from this repository — and `orange_money::refund`
is a declared `NotImplemented` token, which answers a merchant `501`. Neither
rail answers `Unsupported`. **Nothing settles a `pending` refund**, because the
provider port has no refund status read and there is no refund poll ladder
(RFC-0003 open question 8, open). And a refund whose transfer has already been
instructed can no longer be cancelled at all — the money review closed that
double-payout hole, and what the cancel route is left with is a create that
died between committing its row and recording its attempt.

## The one conflict, and how it was resolved

`backends/apps/vpay-server/src/main.rs`, the boot `tracing::warn!` literal. One
hunk. Arm F's contract review and arm G's review had each rewritten the same
string, having found the same false claim by different methods — one by
sweeping the repository for statements that `POST /v1/refunds` was unrouted,
the other by watching a real boot print one while that same process served the
SDKs' live refund suites. Git cannot merge two rewrites of one literal. Arm G's
review predicted this conflict in writing before it happened.

Resolved to a single banner, preferring arm G's wording as its review asked,
and carrying what each side had that the other did not:

| From                | Kept                                                                                                                                 |
| ------------------- | ------------------------------------------------------------------------------------------------------------------------------------ |
| arm G's review      | the narrowed credential clause — no **real** MTN Disbursements credential exists, the only one anywhere is the e2e/demo stack's stub |
| arm G's review      | `NO REFUND HAS EVER MOVED MONEY` and `NOTHING SETTLES A PENDING REFUND`, with the poll ladder named as the reason                    |
| arm F's review      | the consequence clause — an Orange refund fails at once and gives its reservation back                                               |
| neither, added here | **all five** routes named. Arm F's review named paths and listed four; it omitted `GET /v1/refunds/{id}`, routed since 2026-09-05    |

The five in the banner agree with `V1_ROUTES` and with
`the_refund_resource_is_mounted_for_exactly_five_methods`, which pins the
mounted surface as a literal. `justfile` and `compose.e2e.yml` conflicted with
nothing, as arm G's review predicted.

## The correction that had to happen before the merge, not after

`review/w3f-contract` adds
`backends/migrations/0048_refunds-comments-post-v1-refunds-is-routed.sql`. In
three places — its `--` header's WHAT IS CORRECTED bullet, its
`COMMENT ON TABLE refunds` and its `COMMENT ON COLUMN
invoices.amount_refunded` — it said `mtn_momo::refund` runs "against a
credential no deployment holds".

Arm G gives the e2e/demo stack a stub `disbursement_subscription_key`, aimed at
a `wiremock/wiremock` container, so its live refund suites can reach MTN's
documented `202` at all. That sentence is therefore false the day it lands —
and a migration's bytes are checksummed into `MANIFEST.sha256` and into
`_sqlx_migrations.checksum`, so it could never have been corrected in place.
`0047`'s stale wording is the precedent and is in the errata table for exactly
that reason.

All three now say **no REAL MTN Disbursements credential** exists in this
project, naming the stub as the only subscription key anywhere. `0048` has
never shipped, so its bytes are not frozen — the immutability rule protects
APPLIED migrations. The manifest line was regenerated the honest way: the stale
line was removed and `just migrations-manifest` appended a fresh one, because
that recipe refuses to rewrite an existing line. The result is a one-line diff
on `MANIFEST.sha256`.

Numbering was checked: 48 `.sql` files, no two sharing a number, and
`schema_migrates_cleanly_on_an_empty_database` asserts 48.

## The test the merge found red, and why it was not a merge artefact

`postgres_smoke::canceling_a_pending_refund_releases_its_reservation` fails on
this merge. It also fails on `origin/review/w3f-money`: that file is
byte-identical to that branch's, and `cancel_in_tx` is functionally identical
to it, so the case has been red since `4bcf6491` landed the cancel rule. That
branch's gate table re-ran `--test refunds` and clippy after the fix and did
not re-run `--test postgres_smoke`; the postgres_smoke row on its page is arm
F's, from before the rule existed.

The rule refuses a `pending` refund younger than sixty seconds, because a young
refund with no `provider_requests` row cannot be told apart from a create that
is still running and may be about to instruct a rail. The case created a refund
and cancelled it in the same breath, so `Refunds::cancel` answered `Ok(None)`
and its whole subject was unreachable.

Repaired the way the money review repaired the route-level twin: **build the
premise, change no assertion.** The refund is aged ninety seconds, exactly as
`refunds.rs`'s `age_past_the_cancel_window` does for
`a_pending_refund_cancels_once_and_gives_its_reservation_back`. One thing got
stronger: the `merchant_2` refusal above it is a test of tenancy only once the
age predicate can no longer be what refuses it.

## The stale claims the merge created, found by grep rather than by reading

Each of these is false only once arm F's routes and arm G's demo credential are
in one tree, so no arm could have fixed them and no conflict marker pointed at
any of them.

**"no deployment holds a Disbursements subscription key"** — thirty-odd
occurrences, corrected to "no REAL MTN Disbursements credential exists in this
project" in `README.md`, `config/application.yml`,
`deploy/helm/vpay/templates/_validate.tpl`, `schemas/vpay.cstack`, the MTN
adapter's module header and `token.rs`, `vpay-api`'s crate header and
`v1/mod.rs`, `vpay-config`, `vpay-db`'s `refunds.rs` and `settlement.rs` and
its repository tests, the conformance suite, the refunds integration suite,
`backends/migrations/README.md`, and nine pages under `docs/`.

**"`POST /v1/refunds` is unrouted"** — arm F swept eighteen of these; these
were what both sweeps missed. The one that mattered is `docs/flows/errors.md`,
which said "**no `/v1` caller can provoke a `501` at all**". A
`POST /v1/refunds` against an `orange_money` charge answers exactly that, and
`an_unbuilt_rail_refund_fails_and_releases_its_reservation` has asserted the
`501` since arm F. The document said it could not happen.

Left alone on purpose, each saying so in its own text: migration `0047`
(applied, immutable); `docs/status/backend.md` and the dated pages in this
directory, which are archived records with a stated rule against rewriting;
`docs/plans/`; and the verbatim historical quotes in `docs/api/README.md` and
`docs/flows/merchant-auth.md`, which now carry a note naming the clause that
went stale.
