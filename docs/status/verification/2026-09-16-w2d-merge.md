# 2026-09-16 — merging arm D (MTN Disbursements) into the refunds branch

`review/w2d-mtn` merged into `claude/orange-refund-transaction-2b95e5` on
`merge/w2d-into-feature`. Sixteen files conflicted; two more problems were in
files the merge resolved **cleanly**, and they are the reason this page exists.

`just ci` was **not** run — the brief forbade it. What is below is what was
actually run in this worktree, and nothing else is claimed. The host's Node is
v24.20.0 while `.nvmrc` pins 22.23.2, so the prettier run below is the
repository's own `pnpm exec prettier --check .` under a newer engine than CI
uses.

## The two things no conflict marker showed

### 1. Two migrations both numbered `0046`

`0046_ledger-id-length.sql` (RFC-0003 § 3, the refunds branch) and
`0046_refunds-comments-mtn-refund-is-written.sql` (arm D's review) are
different files with the same number. They touch no common line, so both were
kept and `git status` was clean.

`0046_ledger-id-length.sql` keeps `0046`. Arm D's is renumbered to
`0047_refunds-comments-mtn-refund-is-written.sql`, its `MANIFEST.sha256` line
rehashed in the same commit. That is allowed because the file **had never been
applied anywhere**: `sqlx::migrate!`'s immutability rule protects migrations a
database has recorded, and this one is new on a branch. Prose references were
updated in `backends/migrations/README.md`, `docs/runbooks/migrations.md` and
`docs/status/infrastructure.md`; the dated arm-D review page carries a merge
note instead, because rewriting a dated record falsifies it.

**The tripwire that caught it** was not a conflict marker and not
`verify-migrations` — the manifest was consistent either way. It was
`postgres_smoke.rs`'s `schema_migrates_cleanly_on_an_empty_database`, which
pins the applied count: `left: 47, right: 46`. Both branches had set that
number to 46. The assertion's message now names `0047` and says in as many
words that this count is the tripwire for exactly this collision.

### 2. A conformance helper both branches' assumptions had outgrown

`claims_refunds` gated arm D's five refund wire cases on
`Capabilities::supports_refunds`. That was a sound gate on either branch
alone, and false on the merge:

| Rail           | before the merge                         | after                                   |
| -------------- | ---------------------------------------- | --------------------------------------- |
| `mtn_momo`     | `supports_refunds: true`, refund a token | `true`, refund **written**              |
| `orange_money` | `supports_refunds: false` (arm D's view) | `true`, refund a `NotImplemented` token |

So the `orange_money` parameterisation of five container-backed cases started
driving a real transfer at a rail that answers a token.
`a_duplicate_refund_reference_is_accepted_and_never_paid_twice::case_2_orange_money`
**failed**, correctly, on the first conformance run after the merge.

The helper now has three states rather than two, and the third is **not** a
silent skip: a rail that declares the capability and has not built the call
must answer a `NotImplemented` token **naming itself** — never `Unsupported`,
never `Ok`. No case was deleted, no `#[case]` removed and no assertion
loosened; the Orange arm asserts something it did not assert before.

**Mutation, run rather than reasoned about:** replacing Orange's token with a
copy-pasted `NotImplemented("mtn_momo::refund")` makes
`a_duplicate_refund_reference_is_accepted_and_never_paid_twice::case_2_orange_money`
fail with `left: "mtn_momo::refund", right: "orange_money::refund"`. Reverted.

## What `0047` corrects, beyond what arm D wrote

Arm D's migration corrected the MTN half of two shipped `COMMENT ON`
statements. Three further sentences in them had gone false on the refunds
branch, and a `COMMENT ON` is text in every database that applied the
migration — an operator reads it in `\d+`:

| Where                                                 | What it said                                                                        | What `0047` says now                                                                       |
| ----------------------------------------------------- | ----------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------ |
| `0042`'s `COMMENT ON COLUMN invoices.amount_refunded` | "`NotImplemented` on MTN and **`Unsupported` on Orange**"                           | Orange is a `NotImplemented` token; `Unsupported` is neither rail's answer                 |
| `0042`'s GAP note                                     | the refunds insert "does not exist anywhere … `vpay_db::Refunds` exposes no create" | `Refunds::create` **is** that insert (RFC-0003 § 3)                                        |
| `0042`'s GAP note                                     | `payment_intents.amount_refunded` / `amount_refund_pending` "are NOT maintained"    | `apply_refund_succeeded` / `apply_refund_failed` maintain both                             |
| `0017`'s `COMMENT ON TABLE refunds`                   | "NOT WRITTEN OR READ BY ANY CODE IN THIS REPOSITORY"                                | written by `Refunds::create`, read by `GET /v1/refunds/{id}`, reachable from no deployment |

The frozen `0042` and `0017` files were **not** edited. Their `--` headers are
in no database and are recorded in `backends/migrations/README.md` § Errata,
whose three rows were corrected too — including the row that claimed zero
`NotImplemented` tokens remain.

## What is true about refunds in this tree

Stated here because both branches wrote a version of it and only one sentence
can be true:

- `mtn_momo::refund` is **written** — MTN's Disbursements `transfer` — and
  **MTN's Disbursements product has never been called from this repository**,
  in sandbox or anywhere else. No deployment holds the subscription key;
  `config/application.yml` carries the three `${VAR}` names empty and `refund`
  answers `ProviderError::Config` naming the first missing one.
- `orange_money::refund` is a declared `NotImplemented("orange_money::refund")`
  token: an Orange refund is an outbound transfer and this repository has no
  Orange transfer specification.
- **Neither answers `ProviderError::Unsupported`.** `supports_refunds` is
  `true` on both rails, so both gaps are vpay's rather than facts about a rail.
- `vpay_db::Refunds::create` exists and **`POST /v1/refunds` is routed
  nowhere** (wave 3), so nothing in a shipping binary reaches it and no refund
  can be created through `/v1` at all.
- `verify-status` prints **1 unimplemented item** — not 0 (arm D's number) and
  not 2 (the refunds branch's). Two tokens moved on 2026-09-15, in opposite
  directions, on two branches.
