# ADR-0039: OpenTelemetry through the SDK, and dashboards generated from Python

- **Status:** Accepted. **Reverses**, in part, the step-6 decision (6) that deferred OTLP
  ([`docs/plans/2026-09-03-step6-deployment.md`](../plans/2026-09-03-step6-deployment.md)): that decision chose
  `metrics` + `metrics-exporter-prometheus` over the OpenTelemetry SDK and removed the unused `opentelemetry` pin. The
  Prometheus listener it built is **kept, unchanged**; this ADR adds an export beside it.
- **Date:** 2026-11-27
- **Deciders:** the owner, in two rulings relayed on the board (ANR-1165 and its memory `otel-conventions`), both
  2026-11-27, quoted:
  _"all backends should export OTel and we need to build OTel dashboards, important information to watch … We'll have it
  in a grafana or openobserve (another openobserve instance, not the one for our users)"_, and
  _"We'll use opentelemetry libs and json dashboards built with python scripts"_. The rest of this ADR, the allowlists,
  the closed vocabulary, the figures (a queue of 4096, 4096 series, a flush of 5 s) and the choice to keep the Prometheus
  listener, are the implementing change's, put to the owner for review: they are not quotations of a ruling.

## Context

vpay had `/metrics` (Prometheus text, fifteen series), JSON logs with a request id, and no traces and no push export.
The owner wants every backend to export OpenTelemetry to a collector and to ship dashboards for what matters, in code.
Two constraints of this repository decide how:

- **One TLS provider.** `deny.toml` bans `aws-lc-rs` and OpenSSL; `reqwest` is `0.13` with `rustls-no-provider`, and the
  binary installs `ring` once. The OTLP exporter must reuse that client, not bring its own.
- **A payment system's telemetry is a disclosure surface** (ADR-0020, `schemas/privacy-inventory.yaml`). What leaves the
  process must be closed by construction, not by review.

CrateStack `=0.20.4` has no OpenTelemetry exporter (_verified 2026-11-27_ by reading its sources in the cargo registry:
`cratestack-service` has a `tracing_subscriber` formatter and nothing else), so "use CrateStack's exporter" is not
available for vpay's own router either; the SDK is.

## Decision

1. **The SDK, over OTLP/HTTP with JSON bodies.** A new crate, `vpay-telemetry`, uses `opentelemetry` 0.33.1,
   `opentelemetry_sdk` 0.33.1, `opentelemetry-otlp` 0.33.1 (`http-json` and `reqwest-blocking-client`, no `tonic`) and
   `tracing-opentelemetry` 0.34.0. The exporters are handed a client built from the workspace's `reqwest` 0.13 on `ring`;
   the SDK's own client builder is not used. Only `vpay-server` depends on it.
2. **Off unless an endpoint is set.** No endpoint, no providers, no thread, no connection, and the `vpay_telemetry_*`
   series do not exist (a zero there would read as "exporting fine"). Only the `serve` and `worker` modes export; a
   one-shot `staff` or `callbacks` command prints its result on stdout and never opens a connection.
3. **The vocabulary is closed at the exit.** `vpay_core::metrics::ALL` (21 names) and `LABELS` (19 keys) are the only
   metrics and label keys the bridge forwards; a test holds `LABELS` to the labels the module documents. A span leaves
   only with the fields of `filter::FIELDS`, text held to a plain alphabet; events, links and the status message never
   leave; an inbound `traceparent` is never read. A log leaves only with a message of letters, so most of today's log
   lines are exported as `redacted`: the log signal is honest and nearly empty until the messages are written for it.
4. **One recorder, two outputs.** `metrics` allows one global recorder. `Fanout` forwards every registration to the
   Prometheus exporter first and to the OpenTelemetry bridge second, so `/metrics` is byte for byte what it was.
5. **Bounded and never blocking.** Spans and logs wait in a queue of 4096 (batches of 512); a full queue drops and
   counts. At most 4096 metric series are forwarded. Temporality is set explicitly to `Cumulative`. The `OTEL_*`
   variables the SDK would obey silently (per-signal compression, headers, timeout and certificate, the temporality
   preference, the span event and link limits, the batch processors' sizes, propagators, the attribute limits) are
   refused at start with exit 78, and a test holds the list. A flush runs on shutdown, on a thread of its own, with a
   5 s deadline.
6. **Dashboards are JSON generated by standard-library Python.** `tools/dashboards/*.py` write
   `deploy/dashboards/*.json` and its README; CI regenerates them and fails on any difference or untracked file. A test
   (`vpay-telemetry/tests/dashboards.rs`) holds every metric and label a panel queries to the vocabulary, every panel to
   the README, and requires a note on the rail dashboard that says a stub rail reports like a live one. The format is
   Grafana JSON on a Prometheus-compatible data source (the same as openbilling-rs), which an OpenObserve instance's PromQL
   endpoint also serves. _Unverified:_ an import into either.
7. **Six new series, all honest about what they measure.** `vpay_webhook_deliveries_pending` and
   `vpay_webhook_oldest_pending_overdue_seconds` (the delivery backlog, read over the partial index
   `webhook_deliveries_live_idx`, written only when the read succeeded), `vpay_db_pool_connections{state}` and
   `vpay_db_pool_max_connections` (read from the pool's counters with no round trip), and the exporter's own
   `vpay_telemetry_exports_total{signal,result}` and `vpay_telemetry_dropped_total{signal}`.

## What this does not claim

- **No metric says a rail works.** The rail series count port calls to whatever host a rail is configured with; a stub
  host (WireMock in the dev, demo and end-to-end stacks) reports like a live rail, and an adapter that is not written
  reports `not_implemented`. `docs/status.md` remains the only place that says which rails have been called live.
- **Payment-intent states are not exported.** The intent's `status` has no index (migration 0037 says so), so counting by
  state is a scan of the whole table on every sample. The charge state machine is exported as an edge counter
  (`vpay_charge_transitions_total{provider,from,to}`, which existed). An intent-level counter needs either an index or a
  counter at each of the many writers; it is left for its own change.
- **No span for a worker job or a rail call, and no PostgreSQL server metrics.** Server-side PostgreSQL metrics are the
  database operator's exporter's. The dashboards say so.
- **Unverified:** a run against a real collector other than the in-process test collector; the collector's and the store's
  naming of the translated series; an import into Grafana or OpenObserve.

## Consequences

- A new outbound connection exists, to an operator-chosen collector, off by default: `schemas/security-inventory.yaml`
  has it (`otlp_collector`), and `schemas/privacy-inventory.yaml`'s `traces`, `metrics` and `logs` rows say what leaves.
  The `traces` surface was "deliberately absent"; it is now enumerable by `filter::FIELDS`.
- `Health::pool_stats` and `WebhookDeliveries::backlog` are new required methods of two `vpay-db` traits. Their only
  implementer is `PgRepositories`.
- Dependencies, _verified 2026-11-27_: see `docs/status/verification/2026-11-27-opentelemetry-export.md` for `cargo tree`
  and `cargo deny` on this change.
- Moving one of the four OpenTelemetry crates moves all of them; the pin comment in the root `Cargo.toml` says so.

## Alternatives rejected

- **Hand-writing OTLP** (as the platform's `aap-trace-otlp` does): the owner ruled for the libraries on 2026-11-27.
- **Replacing the Prometheus listener with the OTel Prometheus exporter:** it would change `/metrics` for every operator
  who scrapes it today, for no gain the owner asked for.
- **`opentelemetry-appender-tracing` for logs:** it exports every field of every event; the allowlist at the exit needs the
  layer this crate owns.
