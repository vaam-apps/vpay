# Threat model: the `notchpay` rail

- **Written:** 2026-10-20, before the adapter's code, as vaam-apps/vpay#291
  § 10 requires. Revised the same day once the code existed, to name the test
  behind each mitigation that this change built.
- **Method:** STRIDE, per element of the data flow below.
- **Scope:** what [RFC-0012](../../rfc/0012-notchpay-adapter.md) and
  [ADR-0031](../../adr/0031-a-status-read-authenticated-by-a-server-side-key.md)
  add to vpay: one outbound interface (`api.notchpay.co`), two rail secrets per
  account, the payer's phone number going to a new recipient, and inbound
  callbacks on `/provider/notchpay/callback`. The core's own threats (merchant
  authentication, the ledger, the dashboard) are out of scope; nothing here
  changes them.
- **Evidence status:** every mitigation marked **built** has a test named
  beside it. Every one marked **not built** is a gap, stated as one. **Nothing
  in this model has been checked against Notch Pay itself**: no test-mode key
  was available on 2026-10-20, so every claim about what Notch Pay does is
  taken from its documentation and specification (`openapi.yaml` 2.1.0).

## The data flow

```text
                 merchant (/v1, OAuth private_key_jwt)
                          │ confirm, payment_method_data[notchpay][msisdn]
                          ▼
 ┌─────────────────────── vpay-server ────────────────────────┐
 │ serve ── charges row (reference, payer_msisdn) ── Postgres │
 │ worker ── poll_charge ─┐                                   │
 │                        ▼                                   │
 │   vpay-adapter-notchpay ── vpay-notchpay (Client)          │
 │        keys from config: public_key, private_key           │
 └────────┬───────────────────────────────────────▲───────────┘
   TLS    │ POST /payments, POST /payments/{ref},  │ POST /provider/notchpay/callback
          │ GET /payments/{ref}                    │ (unsigned as far as vpay
          │ Authorization: public, X-Grant: private│  can check; anyone can POST)
          ▼                                        │
      api.notchpay.co  ── USSD prompt ──▶ payer's handset
          ▲
          │ the same public key, from anywhere it has leaked
          │ (a merchant's own front end, which Notch Pay's docs invite)
      a third party
```

Trust boundaries crossed: vpay ↔ Notch Pay (outbound, TLS); Notch Pay or
anyone ↔ vpay's callback route (inbound, unauthenticated); the operator's
secret store ↔ vpay's configuration (the two keys); and one boundary vpay does
not control at all, the third party ↔ Notch Pay, which exists because the key
the status read accepts is the one Notch Pay calls public.

## STRIDE

### 1. The outbound calls, vpay → `api.notchpay.co`

| Threat                                                                                                                                               | Kind                   | Mitigation                                                                                                                                                                                                                               | State                                                                                                                                               |
| ---------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------- |
| A host that is not Notch Pay answers the read, and vpay settles a charge on its word                                                                 | Spoofing               | TLS with vendored webpki roots, rustls only (ADR-0005). In livemode the configured host may not be a stub host (`validate_host`)                                                                                                         | **built** before this change, unchanged                                                                                                             |
| A redirect sends `X-Grant` and the payer's number to another host                                                                                    | Information disclosure | The process's one `reqwest::Client` refuses redirects; a `3xx` is `Malformed` and the `Location` is never requested                                                                                                                      | **built**: `redirects_are_refused_and_never_followed` (conformance, `notchpay` row)                                                                 |
| A success is reported for a payment whose amount or currency is not the charge's                                                                     | Tampering              | `complete`, `refunded` and `partialy-refunded` are `Succeeded` only if `amount` is an integer equal to the charge's and `currency` equals the charge's; anything else is `Malformed`                                                     | **built**: `a_success_for_another_amount_or_currency_is_never_a_success` (adapter unit tests)                                                       |
| A status vpay does not know is read as a success or a decline                                                                                        | Tampering              | An undocumented status is `Malformed`, naming it                                                                                                                                                                                         | **built**: `a_status_notch_pay_never_documented_is_not_guessed_at`                                                                                  |
| A `404` that is not "Payment not found" (a wrong base path, an unknown Sync account) is read as "no such payment", and a live payment is resubmitted | Tampering              | Only Notch Pay's own "Payment not found" is `NotFound`; any other `404` is `Config`. Crash-safety needs three `NotFound`s over 60 s before a resubmit, and the resubmit carries the same reference, which Notch Pay answers `409`        | **built**: `only_notch_pays_own_not_found_is_not_found`; the `409` itself is **documentation only** (§ 10 item 4)                                   |
| A large or slow answer exhausts the worker                                                                                                           | Denial of service      | Bodies are read through `read_rail_body`, capped at 256 KiB; every request carries `ProviderConfig::request_timeout`                                                                                                                     | **built**: `an_oversized_rail_body_is_refused_at_the_cap`, `an_unavailable_rail_is_a_transport_error_never_a_decline` (conformance, `notchpay` row) |
| Notch Pay's own error prose, which can quote the payer's number, reaches a log                                                                       | Information disclosure | Every client type that holds rail prose, a reference or a number has a hand-written `Debug` (twelve, registered in `schemas/privacy-inventory.yaml`); a `Rejected`'s rail message prints through `Secret`; transport errors carry no URL | **built** in `vpay-notchpay` (#285); the adapter adds no type that holds one                                                                        |
| A merchant's keys are refused and every charge fails quietly as a decline                                                                            | Denial of service      | `401`/`403` is `Rejected { provider_account_blocked }`, which pages                                                                                                                                                                      | **built**: `bad_credentials_are_not_reported_as_a_payer_problem` (conformance, `notchpay` row)                                                      |

### 2. The keys, operator → vpay

| Threat                                                                                            | Kind                   | Mitigation                                                                                                                                                                                                                                                                                                 | State                                                                                                                                                                                                                                                                                                               |
| ------------------------------------------------------------------------------------------------- | ---------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| A key is printed in a log, an error or a boot message                                             | Information disclosure | Keys live under `credentials`, whose `Debug` is redacted (`ProviderHost`, `ProviderConfig`); the client holds them as sensitive `HeaderValue`s behind `Secret`; the boot warning and every config error name a key, never its value                                                                        | **built**: `keys_never_reach_a_debug_or_an_error` (adapter), `a_notchpay_key_livemode_mismatch_never_prints_the_key` (config)                                                                                                                                                                                       |
| A deployment runs on the public key alone, the weaker shape, by omission                          | Elevation of privilege | `credentials.private_key` is required at boot (ADR-0031 condition 2) and sent on every call (condition 1)                                                                                                                                                                                                  | **built**: `notchpay_requires_both_keys` (config), and every conformance stub matches only requests carrying `X-Grant`                                                                                                                                                                                              |
| A test key reaches a livemode deployment, or a live key a sandbox                                 | Tampering              | In livemode a key containing `test_` refuses to boot; outside livemode a key without it does (RFC-0012 § 2). Notch Pay has one host for both modes, so the key is the only place the rule can sit                                                                                                          | **built**: `a_notchpay_key_must_agree_with_livemode` (config). Whether a live key's prefix is `pk_live_` is **unknown** (§ 10 item 8); the rule only reads `test_`                                                                                                                                                  |
| A livemode deployment takes real payments on the rail without anyone having accepted the exposure | Repudiation            | In livemode boot refuses the rail until its block says `settings.accept_public_key_exposure: true` (ADR-0031 condition 4, amended 2026-10-20). The acceptance is a line of reviewed configuration, not a log line scrolled past. The refusal names the setting and `credentials.public_key`, never a value | **built**: `a_livemode_notchpay_block_without_the_acknowledgement_is_refused`, `the_acknowledgement_refusal_names_the_setting_and_the_key_never_a_value`, `a_livemode_notchpay_block_written_as_the_docs_show_loads` (config); `a_livemode_notchpay_rail_boots_only_acknowledged_and_still_warns` (the real binary) |
| A literal key is committed in a livemode file                                                     | Information disclosure | The existing livemode rule: every credential is a `${VAR}`                                                                                                                                                                                                                                                 | **built** before this change, and covers the new keys because it walks every `credentials` entry                                                                                                                                                                                                                    |

### 3. The public key, third party → Notch Pay (outside vpay)

This is the boundary ADR-0031 accepts rather than closes.

| Threat                                                                                                                     | Kind                     | Mitigation                                                                                                                                                                                                                                                                       | State                                                                                                                                                                                                                                                                                              |
| -------------------------------------------------------------------------------------------------------------------------- | ------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Whoever holds the public key reads the status, amount and customer of any payment on the account                           | Information disclosure   | **None vpay can apply.** vpay keeps the key server-side and never hands it to a browser or an app. The exposure is documented and logged; in livemode the operator must accept it in writing (`settings.accept_public_key_exposure: true`, ADR-0031 condition 4) or boot refuses | **accepted** (ADR-0031). Logged at boot: `the_exposure_is_declared_through_the_port`. The livemode acknowledgement is **built**: `a_livemode_notchpay_block_without_the_acknowledgement_is_refused` (config), `a_livemode_notchpay_rail_boots_only_acknowledged_and_still_warns` (the real binary) |
| …initializes a payment on the account, or processes a pending one to **any** number (a USSD prompt in the merchant's name) | Spoofing                 | As above. A prompt to a stranger is phishing in the merchant's name; vpay never learns of it, because it is not a vpay charge                                                                                                                                                    | **accepted**, documented in [adapter-notchpay.md](../../flows/adapter-notchpay.md) § "Production risks"                                                                                                                                                                                            |
| …cancels a pending payment that is vpay's                                                                                  | Denial of service        | The charge reads `canceled`, which maps to `Failed { provider_error }`, **not** `payer_declined`, precisely because the cancel may not be the payer's (RFC-0012 § 4). The merchant starts a new intent; no money moved                                                           | **built**: the `canceled` row of `every_documented_status_maps_as_rfc_0012_says`                                                                                                                                                                                                                   |
| The merchant embeds the public key in a front end, as Notch Pay's documentation invites                                    | Information disclosure   | Out of vpay's reach. The flow page and the boot warning say so                                                                                                                                                                                                                   | **accepted**                                                                                                                                                                                                                                                                                       |
| Notch Pay starts enforcing `X-Grant` on the read                                                                           | — (the threat goes away) | vpay already sends it on every call, so nothing changes                                                                                                                                                                                                                          | **built**: the conformance stubs refuse a request without `X-Grant`                                                                                                                                                                                                                                |

### 4. The callbacks, anyone → `/provider/notchpay/callback`

| Threat                                                                           | Kind                   | Mitigation                                                                                                                                                                                                                                                    | State                                                                                                                                                                                                |
| -------------------------------------------------------------------------------- | ---------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| A forged webhook says a payment completed                                        | Spoofing               | "Callbacks are hints": `parse_callback` returns identifiers and no status, and the only thing that moves money is the authenticated read. A forged `payment.complete` costs one read                                                                          | **built**: `a_callback_body_round_trips_to_identifiers_only` (conformance), `a_callback_is_identifiers_only_and_carries_no_key_material` (adapter)                                                   |
| A forged webhook plants key material on a charge                                 | Tampering              | The adapter's `CallbackRef::ref_extra` is always empty, and the route discards `ref_extra` anyway                                                                                                                                                             | **built**: same adapter test                                                                                                                                                                         |
| Notch Pay's signature (`x-notch-signature`, HMAC-SHA256) is not checked          | Spoofing               | Not checkable: the port's `parse_callback` receives no headers (RFC-0010 open question 4). What is signed, and whether a captured webhook replays forever (no timestamp), are § 10 item 7                                                                     | **not built**, and out of scope (epic § 5); [RFC-0014](../../rfc/0014-verifying-rail-callbacks.md) (draft) designs it. Without it an unverified webhook is worth one authenticated read and no money |
| A flood of callbacks drives rail traffic                                         | Denial of service      | The route's existing bounds: one `poll:` job per charge, a ten-second pull-forward floor, a 16 KiB body. **There is no rate limit**, and a caller who knows a live charge's reference can hold it at about one read per worker claim (`provider_callback.rs`) | **built** before this change, unchanged, and the stated gap is unchanged too                                                                                                                         |
| A body naming an event vpay does not handle is acted on                          | Tampering              | Only the five payment events in `vpay_notchpay::wire::PAYMENT_EVENTS` are accepted; any other `type`, a non-UUID `data.reference`, or `{}` is `Malformed` and the route answers `400`                                                                         | **built**: `a_callback_for_an_event_vpay_does_not_handle_is_refused`                                                                                                                                 |
| The webhook URL is registered on the account by someone else, pointing elsewhere | Repudiation, Tampering | Out of vpay's reach until RFC-0013: the merchant registers the URL by hand in Notch Pay's dashboard. vpay's correctness does not depend on callbacks arriving — the poll ladder settles every charge without them                                             | **accepted**; vpay registering its own endpoint is vaam-apps/vpay#287                                                                                                                                |

### 5. The payer's number, vpay → a new recipient

| Threat                                                                     | Kind                   | Mitigation                                                                                                                                                                                   | State                                                                             |
| -------------------------------------------------------------------------- | ---------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------- |
| The payer's number goes to Notch Pay without being recorded as going there | Information disclosure | `schemas/privacy-inventory.yaml` lists `notchpay` as a recipient of `payer_msisdn`, which `verify-privacy-inventory` reads                                                                   | **built** in this change                                                          |
| More of the payer's data goes than the charge needs                        | Information disclosure | The initialize body carries `phone` only — no email, no name, no merchant metadata (RFC-0012 § 3). `description` is the deployment's fixed `settings.description`, not merchant input        | **built**: `the_initialize_body_carries_the_phone_and_nothing_else_of_the_payers` |
| Notch Pay holds the number under terms vpay has not read                   | Information disclosure | The operator's due diligence (ADR-0029 D1). The merchant agreement's data clauses are unread by this project; Notch Pay's legal entity and regulator are unpublished (RFC-0012 § 10 item 10) | **not addressed**; recorded                                                       |

## What would change this model

- **Notch Pay answers § 10 item 1 with a yes.** Section 3 then shrinks to
  "the private key, held server-side", the warning is withdrawn, and the rail
  moves to ADR-0031's first limb.
- **The port passes headers to `parse_callback`.** Section 4's signature row
  becomes buildable, and § 10 item 7 decides how.
- **Model B (Sync) is offered.** A platform key reads every connected
  account's payments, which widens § 3 to every merchant on the deployment.
  It is not offered (RFC-0012 § 2), and this model does not cover it.
- **The first sandbox session** (RFC-0012 delivery step 1). Every "documented
  only" above is a claim about Notch Pay's pages until then.
