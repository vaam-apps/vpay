# Step 3 — the rails: implementation-ready design

Decisions taken by the orchestrator (do not reopen): (1) Step 3 starts only after Step 2 merges;
(2) the vendored-roots HTTP client moves to `vpay_provider::http` (re-exported from vpay-api);
(3) `mtn_momo::refund` keeps its `NotImplemented` token (Disbursements is a different product with
credentials no deployment has) — seven tokens go, one stays; (4) Orange `merchant_key` stays in
`credentials`; (5) push-rail recovery stays in Step 4 and docs/roadmap.md Phase 4 is split in the
same commit; (6) drop vpay-testkit's unused runtime `wiremock` dependency now and extend
`verify-no-mocks` to scan every non-dev edge reachable from a shipping binary via `cargo metadata`
(P owns it if small, else a follow-up); (7) add `Money::to_provider_minor(self) -> i64` beside
`to_provider_string`, documented in money.md.

## 1. Port

```rust
// vpay-provider/src/lib.rs
#[async_trait::async_trait]
pub trait ProviderAdapter: std::fmt::Debug + Send + Sync {
    fn code(&self) -> &'static str;
    fn capabilities(&self) -> Capabilities;
    async fn submit(&self, charge: &ChargeRef, config: &ProviderConfig)
        -> Result<Submitted, ProviderError>;
    async fn query_status(&self, charge: &ChargeRef, config: &ProviderConfig)
        -> Result<ChargeStatus, ProviderError>;
    fn parse_callback(&self, body: &[u8]) -> Result<CallbackRef, ProviderError>; // stays sync
    async fn refund(&self, _c: &ChargeRef, _a: Money, _cfg: &ProviderConfig)
        -> Result<Submitted, ProviderError> { Err(ProviderError::Unsupported) }
}
```
`async-trait = "0.1"` is already in `Cargo.lock:181` (via authkestra-op/vpay-db); add it to `[workspace.dependencies]`. `ChargeRef`, `Submitted`, `ChargeStatus`, `CallbackRef`, `RefExtra`, `ProviderError` are unchanged — `ChargeStatus::NotFound` (`lib.rs:81`) is already the canonical answer Step 4 needs. `ChargeRef.ref_extra: RefExtra` (`lib.rs:56`) is how Orange's `pay_token` reaches `query_status`; `Submitted.ref_extra` (`lib.rs:63`) is how it comes back.

`ProviderConfig` gains nothing structurally — it already has every field. What changes is who fills it:

```rust
pub struct ProviderConfig {
    pub base_url: String,      // MTN: host only. Orange: host + /orange-money-webpay/{env}
    pub callback_url: String,
    pub currency: vpay_core::Currency,
    pub settings: BTreeMap<String, String>,
    pub credentials: BTreeMap<String, String>,
    pub connect_timeout: Duration,   // NEW, default 5s
    pub request_timeout: Duration,   // NEW, default 20s
}
```
Timeouts belong on `ProviderConfig`, not the client: one client is shared across rails, and the WireMock conformance suite needs a short timeout to assert `Transport` without a 20 s test.

Settings/credentials keys, verbatim:

| rail | `settings` | `credentials` |
|---|---|---|
| `mtn_momo` | `target_environment`, `api_user` | `subscription_key`, `api_key` |
| `orange_money` | `env` (path segment, informational), `merchant_key`, `lang` | `client_id`, `client_secret` |

`merchant_key` is not secret (it appears in the request body and is per-merchant, not a bearer); putting it in `settings` keeps `validate_secret`'s livemode `${VAR}` rule meaningful. `api_user` is a UUID, not a secret. **This contradicts today's `application.yml:46`, which has `merchant_key` under `credentials` — P must move it and update the `${ORANGE_MERCHANT_KEY}` plumbing or leave it in `credentials`; pick one and state it.**

**HTTP client home: move `vpay-api/src/http_client.rs` verbatim into `vpay-provider/src/http.rs`.** Justification: `vpay-api → vpay-provider` already (`vpay-api/Cargo.toml:15`), so the dependency direction only works downward; the adapters already depend on `vpay-provider`; and a new `vpay-http` crate would add a workspace member, a `deny.toml`/`verify-errors` registration, and a second place for the `sdks/rust` twin note. Cost, stated plainly: `vpay-provider` stops being transport-agnostic — a future non-HTTP rail links reqwest for nothing. It adds **no new package** to any graph (reqwest 0.13, rustls, webpki-roots are all already resolved in both binaries). `vpay-api::http_client` becomes `pub use vpay_provider::http as http_client;` so `resource_auth.rs:114,517` and `jwks_cache.rs:358` do not change. `HttpClientError` moves with it (its `Classify` impl at `http_client.rs:86-99` is what `verify-errors` counts — the count stays 11, the owning crate changes).

Signature added alongside the existing `client()`:
```rust
pub fn client_with_timeouts(connect: Duration, request: Duration)
    -> Result<reqwest::Client, HttpClientError>;
```
(the "grow a `builder()` sibling" the module doc at `http_client.rs:127-136` already anticipates). Both binaries build **one** client at boot and hand a clone to each adapter.

**Step 2 call-site deltas (P owns, after C merges):** `vpay-server/src/lib.rs` →
```rust
pub fn adapters(http: reqwest::Client) -> BTreeMap<String, Box<dyn ProviderAdapter>>
```
built from `vpay_adapter_mtn_momo::Adapter::new(http.clone())` / `vpay_adapter_orange_money::Adapter::new(http)`; `adapter_registry()` keeps its signature by building a throwaway client — or, better, becomes `fn adapter_codes() -> [&'static str; 2]` so `main.rs:184`'s log line does not build TLS. Same four lines duplicated into `vpay-worker-bin/src/main.rs` (D6). In `confirm` step 5, `adapter.submit(&charge_ref, &cfg)` gains `.await`. **Nothing else in §4's steps 1–6 changes**: the write-first ordering, the `provider_requests` NULL row, and `record_response` are all still correct — only step 6's terminal state stops being uniformly `not_implemented`.

`ResourceConfig` (Step 2 §4) must now carry a real `ProviderConfig` per rail; the conversion `ProviderHost → ProviderConfig` lives in **vpay-config** as `impl ProviderHost { pub fn to_provider_config(&self, deployment: &Deployment) -> Result<ProviderConfig, ConfigError> }` — `callback_url` derived as `{public_base_url}/provider/{code}/callback` unless overridden.

## 2. MTN MoMo

`Adapter { http: reqwest::Client, token: tokio::sync::RwLock<Option<CachedToken>> }`, `CachedToken { value: String, expires_at: Instant }`. Cache keyed by nothing (one config per code today) — **but the trait passes `&ProviderConfig` per call, so a second merchant on the same rail would silently reuse the first's token.** Guard it: store `credentials_fingerprint: [u8; 32]` (SHA-256 of `subscription_key` + `api_user`) in `CachedToken` and re-mint on mismatch. Refresh at `expires_in - 60 s`. In-memory only, no DB.

| call | method/path | headers |
|---|---|---|
| token | `POST {base}/collection/token/` | `Authorization: Basic b64(api_user:api_key)`, `Ocp-Apim-Subscription-Key` |
| submit | `POST {base}/collection/v1_0/requesttopay` | `Authorization: Bearer`, `Ocp-Apim-Subscription-Key`, `X-Reference-Id: {reference_id}`, `X-Target-Environment`, `X-Callback-Url`, `Content-Type: application/json` |
| status | `GET {base}/collection/v1_0/requesttopay/{reference_id}` | Bearer, subscription key, `X-Target-Environment` |

Body per `adapter-mtn-momo.md:36-38`; `amount` = `Money::to_provider_string()`, `externalId` = charge id, `payer.partyId` = `ChargeRef.payer_ref` (absent → `ProviderError::Config("mtn_momo: payer_ref required on a push rail")`).

`submit` outcomes: **202 → `Submitted { ref_extra: empty, redirect_url: None }`**. **409 → also `Submitted`, not an error** (`adapter-mtn-momo.md:61-62`; conformance asserts this). 401 → refresh token once, then `Rejected{ProviderAccountBlocked}`. 400 → map body `code` through the table. **500 → parse `code` from the JSON body first** (`INVALID_CURRENCY`, `NOT_ALLOWED_TARGET_ENVIRONMENT`, `INVALID_CALLBACK_URL_HOST` → `Config`; `INTERNAL_PROCESSING_ERROR` → `Transport`, because the doc says it can mean either); a 500 with a non-JSON body → `Transport`. Never blind-retry a 500.

Mapping table is `adapter-mtn-momo.md:48-59` transcribed verbatim into a `const` array, with a unit test that every row round-trips and an unknown string yields `ProviderError`/`FailureCode::ProviderError` carrying the raw reason.

`query_status`: `PENDING` → `Pending`; `SUCCESSFUL` → `Succeeded { provider_txn_id: financialTransactionId }`; `FAILED` → `Failed { code: map(reason), raw }`; **404 → `ChargeStatus::NotFound`** (never `Failed`); 5xx/timeout → `Err(Transport)`.

`parse_callback`: MTN POSTs the same status body to `X-Callback-Url`; the reference is **not** in the body — it is recovered from `externalId`/`referenceId` if present, otherwise from the URL path. Since the port's `parse_callback(&self, body: &[u8])` has no URL argument, **the reference must come from the body's `externalId`**, and that is our charge id, not the `reference_id: Uuid` `CallbackRef` requires (`vpay-provider/src/lib.rs:88`). **There is no verification of any kind on this callback** — unsigned, unauthenticated. Say so in the doc; the reconciler treats it as a hint (`reconciler.md:36-53`).

`refund`: MTN refunds are a **different product** (Disbursements — `adapter-mtn-momo.md:3,18-24`) with its own subscription key and its own token scope. Nothing in `application.yml` or `ProviderHost` carries a disbursement key. **Buildable now: nothing. Leave `ProviderError::NotImplemented("mtn_momo::refund")` and keep that one token in `docs/status.md` — seven tokens removed, not eight.**

## 3. Orange Money

One base URL in config, per `adapter-orange-money.md:48-50`. Derive the token URL by taking scheme+authority only:
```rust
fn token_url(base: &str) -> Result<String, ProviderError>  // "http://h:8080/orange-money-webpay/dev" -> "http://h:8080/oauth/v2/token"
```
Unit-test it against both `application.yml:43`'s value and `https://api.orange.com/orange-money-webpay/dev`. Token: `POST`, `Authorization: Basic b64(client_id:client_secret)`, form `grant_type=client_credentials`; cached exactly as MTN's.

`submit` → `POST {base}/v1/webpayment` with the body at `adapter-orange-money.md:33-35`; `order_id` = `reference_id.to_string()`, `amount` integer, `notif_url` = `config.callback_url`, `return_url`/`cancel_url` from `settings` (fall back to `callback_url`). Response → `Submitted { ref_extra: {"pay_token": …, "notif_token": …}, redirect_url: Some(payment_url) }`. **The commit-gates-redirect rule is not enforceable inside the adapter** (`crash-safety.md:53-75`) — the adapter's only obligation is to return `ref_extra` *and* `redirect_url` in the same value so a caller physically cannot have one without the other. The enforcement is Step 2's `confirm`: persist `provider_ref_extra` + `redirect_url` in one `UPDATE`, commit, *then* build `next_action`.

`query_status` → `POST {base}/v1/transactionstatus` with `{order_id, amount, pay_token}` read from `ChargeRef.ref_extra["pay_token"]`. Missing `pay_token` → `ProviderError::Config`, **not** `NotFound`. Map per `adapter-orange-money.md:55-59`: `INITIATED|PENDING` → `Pending`; `SUCCESS` → `Succeeded{txnid}`; `EXPIRED` → `Failed(PayerTimeout)`; `FAILED` → `Failed(ProviderError)` unless a recognised sub-reason; HTTP 404 → `NotFound`.

`parse_callback`: `order_id` → `reference_id`; carry `pay_token` into `ref_extra` **if present**. Verification is `notif_token` equality against the stored one — the adapter cannot do it (no state), so it returns `ref_extra: {"notif_token": …}` and the callback route compares. Fail closed: no `notif_token` in the body → `Malformed`.

Seven "to confirm" items (`adapter-orange-money.md:73-83`) and what each blocks: **(1) blocks `parse_callback`'s repair path** — build against the prior, return `pay_token` only when the key is there; **(2) blocks callback verification** — implement `notif_token` equality and nothing else; **(3) blocks livemode config only** — no code; **(4) blocks Step 4's escalation policy** — no code; **(5) keeps `refund` a capability-driven `Unsupported`, not `NotImplemented`** (change `orange_money::refund`'s body from `NotImplemented("orange_money::refund")` to the trait's default `Err(Unsupported)` — that removes the token and makes `refund_is_refused_when_the_capability_is_absent` assert the real thing); **(6),(7) block nothing in code.**

## 5. Conformance suite

1. **Does Step 3 wait for Step 2 to merge, or branch from it mid-flight?**
   *Default: wait.* Gained: no conflicts in `vpay-api/src/lib.rs` and both `main.rs`, and `RouterDeps.adapters` exists to hang `ProviderConfig` off. Lost: Step 3 is serialised behind Step 2 rather than overlapping, and P sits idle. 2. **Where does the vendored-roots client live: `vpay-provider::http`, or a new `vpay-http` crate?**
   *Default: `vpay-provider::http`.* Gained: no new workspace member, no new `deny.toml`/`verify-errors` registration, `vpay-api` keeps a one-line re-export so no existing call site changes. Lost: `vpay-provider` — the *port* — now depends on reqwest/rustls/webpki-roots, so a future non-HTTP rail (USSD gateway, file drop) links a TLS stack it never uses, and the crate's doc claim of being pure interface stops being true.

3. **`mtn_momo::refund`: leave the `NotImplemented` token, or build Disbursements now?**
   *Default: leave it.* Gained: honest status page, and no invented `disbursement_subscription_key` config that no deployment has ever been issued.    *Default: keep it in `credentials`, where `application.yml:46` already puts it.* Gained: no change to the existing `${ORANGE_MERCHANT_KEY}` plumbing, and it stays out of `ProviderHost`'s `Debug`. Lost: the livemode `${VAR}`-only rule (`validate_secret`) is then enforced on a value that is not really a secret, which is friction at onboarding for no security gain — and it muddies what `credentials` means for the next rail.
