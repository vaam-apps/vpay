# exp26 — the UI revamp: Base UI + daisyUI everywhere, measured

Plan only. Nothing in this document has been built. It is written against
`7d52421` (master + PR #74, the checkout-page restyle) and every number in it
was measured on that tree on **2026-09-07**, not estimated.

## The requirement

> "For the UI library, I still see raw tailwind here and there. Please, remove
> that. In fact, use base-ui + daisyui. I should see a min 80% reduce in ui
> components and css classes. When cva + tw-merge + clsx are used, the code
> should be elegant. … No UI fidelity to keep here, we have still no visual
> identity."
> — the maintainer, 2026-09-07

Standing preferences from 2026-09-05 that this plan carries forward: daisyUI
theme **bumblebee**, Base UI component defaults, minimal custom styling, popup
rather than iframe, `branding.yaml`/`config.yaml` read at runtime.

## 0. Two findings that change the shape of the work

Read these before the lane split. Both were checked against the live npm
registry and the vendors' own documentation on 2026-09-07, and both contradict
what is currently written down in this repository.

### 0.1 `@base-ui-components/react` is deprecated. Base UI has been stable since December.

`frontends/apps/checkout/package.json` pins `@base-ui-components/react`
`1.0.0-rc.0`, and `docs/plans/exp21-checkout-page-notes/opus.md` §2.1 records
"that package has no stable release; `latest` is the release candidate" as a
maintainer decision. **That is no longer true, and it was already stale when it
was written.** The package was *renamed*:

```
$ npm view @base-ui-components/react@1.0.0-rc.0 deprecated
Package was renamed to @base-ui/react

$ npm view @base-ui/react dist-tags
{ "latest": "1.8.0" }

$ npm view @base-ui/react time      # abbreviated
"1.0.0-rc.1": "2025-12-11T10:19:03.495Z"
"1.0.0":      "2025-12-11T15:56:18.070Z"
"1.8.0":      "2026-09-04T08:52:51.986Z"
```

So the payment page is pinned to a **deprecated release candidate of a package
that no longer receives releases**, nine months after that package went 1.0 and
three days after its eighth minor. The `latest` tag on the old name still reads
`1.0.0-rc.0` forever, which is exactly why "we checked, it is still rc" kept
being true and kept being wrong.

Consequences for this plan:

- `1.0.0-rc.0 → 1.8.0` is not an upgrade inside a major, it is a package
  change. Import paths move from `@base-ui-components/react/checkbox` to
  `@base-ui/react/checkbox`.
- The exp21 risk "a pre-1.0 dependency on a payment page" **is retired**. That
  is the single biggest reduction in this plan's risk budget and it costs
  nothing.
- The component surface is now much wider than rc.0's, and it covers the whole
  component set below. Public subpaths in 1.8.0:
  `button field fieldset input select checkbox checkbox-group radio radio-group
  switch toggle toggle-group toolbar toast dialog alert-dialog drawer popover
  tooltip preview-card menu menubar context-menu navigation-menu tabs accordion
  collapsible scroll-area separator avatar progress meter slider number-field
  otp-field combobox autocomplete form direction-provider csp-provider
  use-render merge-props`.
- **`@base-ui/react/drawer` exists.** `@vpay/ui`'s `PayerSheet` is currently
  `vaul` + `framer-motion`; both dependencies can be deleted outright.
- Peers are `react`/`react-dom` `^17 || ^18 || ^19` plus `date-fns`,
  `@date-fns/tz` and `@types/react`, and all three of those are
  `peerDependenciesMeta.optional: true` — checked, because `.npmrc` sets
  `strict-peer-dependencies=true` and `auto-install-peers=false`, under which a
  non-optional peer would fail the install.
- Base UI's checkbox **still** renders `<span role="checkbox">` with a hidden
  input by default, so exp21's §2.2 finding stands. What is new in 1.8.0 is an
  escape hatch: `nativeButton` + `render={<button />}`. Lane A decides; the
  a11y assertions stay either way.

### 0.2 `tailwind-merge` 3.6.0 forces Tailwind 4, which forces daisyUI 5.

The maintainer named 3.6.0 and 3.6.0 is correct (`npm view tailwind-merge
version` → `3.6.0`). It is not a free bump:

> "This release drops support for Tailwind CSS v3 and in turn adds support for
> Tailwind CSS v4. That means you should upgrade to Tailwind CSS v4 and
> tailwind-merge v3 together."
> — `dcastil/tailwind-merge`, `docs/changelog/v3-changelog.md`

And daisyUI's own install skill:

> "daisyUI 5 requires Tailwind CSS 4. In this version, the `tailwind.config.js`
> file is deprecated and should not be used."
> — `saadeghi/daisyui`, `skills/daisyui/install/SKILL.md`

The repository is on `tailwindcss ^3.4.17`, `daisyui ^4.12.23`,
`tailwind-merge ^2.6.0`. So there is exactly one coherent target and one
coherent status quo, and no half step:

| | today | after |
|---|---|---|
| tailwindcss | 3.4.17 | **4.3.3** |
| daisyui | 4.12.23 | **5.7.28** |
| tailwind-merge | 2.6.0 | **3.6.0** |

**This is the decision the whole plan hangs on and it is not reversible
per-lane.** Taking the maintainer's `tailwind-merge` 3.6.0 means taking the
Tailwind 4 migration and the daisyUI 5 class renames in the same change.
Section 8 costs that out.

deflating it. The measurement is conservative against the reduction claimed.

### What the baseline actually says

Three things, and none of them is "there is raw Tailwind everywhere":

1. **`examples/shop` has no Tailwind at all.** It is 229 lines of hand-written
   CSS with semantic class names (`.card`, `.wrap`, `.status-paid`) plus **24

   the one place the word "Tailwind" never appears.
2. **The checkout page is already almost entirely daisyUI**, post-#74: of its
   71 distinct tokens, roughly half are daisyUI component classes

   type utilities (`flex flex-col gap-* mt-* p-4 opacity-* text-*`). The "raw
   Tailwind" the maintainer sees is real but it is layout, not colour.
3. **Only 20 of 106 shipping files make a styling decision at all.** The

### The pattern, once, in full

```tsx
// frontends/packages/ui/src/components/button.tsx
'use client';

import { mergeProps } from '@base-ui/react/merge-props';
import { useRender } from '@base-ui/react/use-render';
import { cva, type VariantProps } from 'class-variance-authority';

import { cn } from '../cn';

/**
 * Every visual decision this component makes, in one map.
 *
 * Nothing below this constant writes a class name, and nothing above it writes
 * a colour: `btn-primary` resolves through daisyUI's `--color-primary`, which
 * `branding.yaml` retints at runtime. See docs/flows/hosted-checkout.md.
 */
const button = cva('btn', {
  variants: {
    variant: {
      primary: 'btn-primary',
      ghost: 'btn-ghost',
      outline: 'btn-outline',
      danger: 'btn-error',
    },
    size: { xs: 'btn-xs', sm: 'btn-sm', md: '', lg: 'btn-lg' },
    block: { true: 'btn-block', false: '' },
  },
  defaultVariants: { variant: 'primary', size: 'md', block: false },
});

export interface ButtonProps
  extends useRender.ComponentProps<'button'>,
    VariantProps<typeof button> {}

/**
 * A button.
 *
 * `render` is Base UI's composition escape hatch: `render={<Link href="…" />}`
 * makes this a link that looks and behaves like a button, which is what
 * `examples/shop` needs and what a hand-rolled `asChild` would have to
 * reimplement. React 19 passes `ref` as an ordinary prop, so there is no
 * `forwardRef` here and there should not be one.
 */
export function Button({ variant, size, block, className, render, ...rest }: ButtonProps) {
  return useRender({
    defaultTagName: 'button',
    render,
    props: mergeProps<'button'>(
      { type: 'button', className: cn(button({ variant, size, block }), className) },
      rest,
    ),
  });
}
```

Call sites, for contrast with what is there today:

```tsx
<Button block>{t('msisdn.submit', { amount })}</Button>
<Button variant="ghost" size="sm" onClick={onBack}>{t('msisdn.back')}</Button>
<Button render={<Link href={`/orders/${order.id}/embedded`} />} variant="outline">
  Pay this order without leaving the shop
</Button>
```

### `cn()` must be taught daisyUI, or it is decoration

`twMerge` knows Tailwind's own class groups. It knows nothing about daisyUI, so
today `cn('btn btn-primary', 'btn-ghost')` returns **both** and the last one
does not reliably win — which is the entire promise `cn` is making at every
override site. Lane A fixes this with `extendTailwindMerge`:

```ts
// frontends/packages/ui/src/cn.ts
import { type ClassValue, clsx } from 'clsx';
import { extendTailwindMerge } from 'tailwind-merge';

/**
 * daisyUI's component modifiers, as conflict groups.
 *
 * Without this, `cn('btn btn-primary', 'btn-ghost')` keeps both — so an
 * override prop silently does nothing, which is worse than not offering one.
 * One group per daisyUI component whose modifiers are mutually exclusive.
 */
const twMerge = extendTailwindMerge({
  extend: {
    classGroups: {
      'daisy-btn-variant': [{ btn: ['primary', 'secondary', 'accent', 'neutral',
        'info', 'success', 'warning', 'error', 'ghost', 'link', 'outline', 'soft', 'dash'] }],
      'daisy-btn-size': [{ btn: ['xs', 'sm', 'md', 'lg', 'xl'] }],
      'daisy-badge-variant': [{ badge: ['primary', 'secondary', 'accent', 'neutral',
        'info', 'success', 'warning', 'error', 'ghost', 'outline', 'soft', 'dash'] }],
      'daisy-badge-size': [{ badge: ['xs', 'sm', 'md', 'lg', 'xl'] }],
      'daisy-alert-variant': [{ alert: ['info', 'success', 'warning', 'error'] }],
      // …input, select, checkbox, radio, tab, loading, card, table
    },
  },
});

export function cn(...inputs: ClassValue[]): string {
  return twMerge(clsx(inputs));
}
```

**Acceptance for this file is a unit test, not a review:** for each group,
`cn('btn btn-primary', 'btn-ghost') === 'btn btn-ghost'`. Deleting one group
entry must fail that test. This is the mutation the reviewer runs (§7).

### What "elegant" means here, as rules a gate can read

1. No `className` string longer than one line. Enforced by
   `eslint-plugin-better-tailwindcss`'s line-wrapping rule (§9).
2. No ternary or template literal assembling class names. Variants live in
   `cva` and only in `cva`. `` className={`alert mt-4 ${tone}`} `` — today's
   `OutcomePanel` — becomes an `Alert` with a `tone` variant.
3. No variant map duplicated across packages. A `cva` call outside
   `frontends/packages/ui/src/components/` is a lint failure.
4. No raw `bg-*` / `text-*` / `border-*` colour utility outside `@vpay/ui`.
   Theme tokens only, and status tone still comes from `@vpay/tokens`
   (AGENTS.md). Grep-gated (§9).
5. No `!important` anywhere in TS or CSS, with **one** exemption that already
   exists and stays: the `prefers-reduced-motion` block in
   `frontends/apps/checkout/app/globals.css`, whose comment already explains
   why it is load-bearing. The gate carries that path as its only allowance.
6. No inline `style={{…}}` outside `@vpay/ui`. Zero, not "few": today's 24 are
   all in `examples/shop` and all are `color`, `fontSize`, `gap` or `marginTop`.

### When a wrapper is allowed, and when raw utilities are

**A wrapper is allowed when** either a Base UI primitive exists for the
behaviour, or daisyUI has a component class for the look. Both, ideally.
Neither, and it is not a component — it is markup, and it belongs in the app.

**Raw utilities are allowed only inside `frontends/packages/ui/src/`, and only
for the layout daisyUI does not cover.** The permitted set, exhaustively:

- flex/grid box model — `flex`, `grid`, `flex-col`, `flex-wrap`, `items-*`,
  `justify-*`, `gap-*`, `space-y-*`
- spacing and sizing — `p-*`, `px-*`, `py-*`, `m-*`, `mt-*`, `mx-auto`, `w-*`,
  `h-*`, `max-w-*`, `min-h-*`, `shrink-0`, `self-*`
- typography that is not colour — `text-xs`…`text-3xl`, `font-medium`,
  `font-semibold`, `uppercase`, `tracking-*`, `tabular-nums`, `break-all`,
  `whitespace-nowrap`, `truncate`
- position/overflow — `fixed`, `absolute`, `relative`, `inset-*`, `overflow-*`
- accessibility — `sr-only`
- opacity — `opacity-*`

Anything else — and every colour utility without exception — is a bug report
against this list, not a licence to write it.

## 6. Risks, with mitigations

### 6.1 Base UI on a payment page

**Retired, and that is the finding (§0.1).** `@base-ui/react@1.8.0` is a stable
release with eight minors behind it. The remaining risk is the *migration*:
rc.0 → 1.8.0 spans nine months of API change on a package that reached 1.0 in
between. Mitigation: Lane B migrates one primitive at a time
(`Checkbox`, then `Field`), running `@vpay/checkout`'s 448 cases after each, and
records any API delta in the lane note. **Do not migrate blind and run the
suite once at the end.**

Second-order: Base UI 1.8.0 ships `@base-ui/react/csp-provider`. The checkout
page has a strict CSP built by `middleware.ts`. Lane B **checks whether Base UI
1.8.0 injects any inline style** and, if it does, wires the CSP provider — a
component library that silently needs `style-src 'unsafe-inline'` on a payment
page is not a component library this repository can take.

### 6.2 Tailwind 4 blast radius

- `@tailwind base/components/utilities` → `@import "tailwindcss"`. Four files.
- `tailwind.config.ts` deleted in three apps; content globs become `@source`.
- `postcss.config.js`: `tailwindcss` + `autoprefixer` → `@tailwindcss/postcss`.
  `autoprefixer` is removed from three `devDependencies`.
- `@apply`: **zero sites in the repository** (measured — the `apply_sites`
  column is 0 across the board). This is the single biggest Tailwind-4
  migration hazard and this repository does not have it.
- Prettier: the repo has **no** `prettier-plugin-tailwindcss` and no
  `.prettierrc` at all, so there is no class-sorting plugin to keep in sync
  with the major. Do not add one in this change; class order is
  `eslint-plugin-better-tailwindcss`'s job (§9) and two sorters disagreeing is
  a formatting war.
- `just fmt` runs `prettier --write .` over ~222 files. **Do not run it**
  (exp21 already recorded this); run `prettier --write` on the lane's own paths.

### 6.3 daisyUI 5 class renames — the silent failure

**This is the highest-risk item in the plan, because it does not error.** A
daisyUI 4 class that daisyUI 5 removed still parses, still renders, and simply
stops styling anything. Every test keeps passing. The upgrade guide's own words:

> "The `form-control`, `label-text`, and `label-text-alt` classes have been
> removed. While existing HTML structures may remain, these classes no longer
> provide styling such as color, font-size, or flex properties."

Classes this repository uses that are affected, measured against the token list
in §2:

| class | in | daisyUI 5 |
|---|---|---|
| `form-control` | `MsisdnForm` | **removed** — use `fieldset` |
| `label-text` | `MsisdnForm` | **removed** — use `label` |
| `input-bordered` | `MsisdnForm` | now the default; `input-ghost` is the borderless one |
| `select-bordered` | `LocaleSwitch` | same |
| `card-compact` | not used | → `card-sm` |
| `btn-group`, `input-group` | not used | → `join` |
| `tabs-bordered/lifted/boxed` | not used yet — **Lane D must not write them** | → `tabs-border`/`tabs-lift`/`tabs-box` |

**Mitigations, all three:**
1. `just verify-ui` greps for the removed daisyUI 4 names and fails the build
   (§9). A grep is the right tool precisely because the compiler will not help.
2. Lane A renders every component in Storybook under `bumblebee` and **looks at
   it**. "Renders without error" is not "renders correctly" (CLAUDE.md).
3. Lane B regenerates the four screenshots in
   `docs/plans/exp21-checkout-page-notes/` using the harness recorded in that
   note's §4, and diffs them. Pixels are the only thing that catches a class
   that stopped doing anything.

### 6.4 Tailwind 4 `@source` under `node-linker=isolated`

`.npmrc` sets `node-linker=isolated`, so `@vpay/ui` reaches each app through a
symlink into `.pnpm`. Tailwind 4 does not scan `node_modules` unless told to,
and a `@source` naming a package specifier resolves through that symlink in a
way that has bitten other monorepos. **Mitigation: `@source` uses relative
monorepo paths only** (§4.4), never `@source "@vpay/ui"` and never a
`node_modules` path.

**Decisive check, and it must be on the built CSS rather than on a render:**
after Lane A, `pnpm --filter @vpay/checkout build` then assert that
`.next/static/css/*.css` contains `.btn-primary` and `.badge-success`. A
component that renders `class="btn btn-primary"` against a stylesheet where
that rule was never generated looks fine in jsdom and is unstyled in a browser.

### 6.5 Hydration — React #418, and theme colour injection

`app/layout.tsx` carries a long comment about React error #418 (*hydration
failed*) taking out all three `shop-hosted.cy.ts` tests when the theme override
was rendered inside an explicit `<head>`. The fix — React 19's
`href`/`precedence` style hoisting — **must not be undone**, and this revamp
touches that file.

Mitigations: `src/layout.test.tsx` asserts the rendered element and stays;
`THEME_OVERRIDE_HREF` and `THEME_OVERRIDE_PRECEDENCE` keep their values;
`shop-hosted.cy.ts` is the decisive check, and a hydration error is *uncaught*
in a real browser, so a green vitest run proves nothing here. Reviewer mutation:
move the `<style>` back inside an explicit `<head>` and confirm
`shop-hosted.cy.ts` fails.

### 8.5 `src/config/theme.ts` collapses

Today: 176 lines converting `#rrggbb` → OKLCh with Ottosson's matrices, plus
daisyUI 4's `cutNumber`/`colorObjToString` reproduced byte for byte, plus a test
file asserting the output against daisyUI 4's own culori-based converter for six
colours.

Under daisyUI 5, `--color-primary` takes **any CSS colour**, so the entire sRGB
→ OKLCh conversion is dead code. What remains necessary is the *foreground*:
daisyUI does not derive `--color-primary-content` for you, and the rule is "80 %
of the way from the colour to white if it is dark, to black if it is light".

Proposed replacement, ~40 lines:

```ts
export function themeStyleSheet(primaryColor: string | null): string | null {
  if (primaryColor === null) return null;
  const rgb = linearRgb(primaryColor);          // kept: it also validates #rrggbb
  if (rgb === null) return null;                // kept: null, never a fallback colour
  const towards = isDark(rgb) ? 'white' : 'black';   // kept: daisyUI's own test
  return `:root[data-theme="${THEME}"]{`
    + `--color-primary:${primaryColor};`
    + `--color-primary-content:color-mix(in oklch, ${primaryColor} 20%, ${towards});`
    + `}`;
}
```

Deleted: `toOklch`, `foreground`, `cut`, `format`, `primaryOverride`, the
`PrimaryOverride` interface, and the six-colour comparison test.
Kept: `linearRgb` (it is the `#rrggbb` validator as much as a converter),
`isDark`, and the guarantee the module's header actually makes — *nothing but
digits and punctuation from a re-validated `#rrggbb` reaches the document*.
`color-mix` in the emitted string is a literal, not an input.

**Two things Lane B must prove rather than assume:**
1. That `color-mix(in oklch, …)` reproduces daisyUI's foreground closely enough
   to pass contrast. The old tests compared against daisyUI's converter; the new
   test must be a **contrast assertion** (axe, or a computed WCAG ratio ≥ 4.5:1
   for six colours including `#ffffff`, `#000000` and `#1d4ed8`), because that
   is the property anyone actually cares about.
2. That the emitted string still cannot carry anything but a validated colour.
   The existing mutation — *"`themeStyleSheet` emits an unvalidated colour"* —
   must still fail.

If `color-mix` turns out not to hold contrast, the fallback is to keep
`isDark` + `foreground` + a `oklch(…)` literal and delete only the sRGB→OKLCh
*output formatting*. That is still a 100-line cut. **Lane B decides on the
measurement, and reports which.**

## Appendix A — `exp26-plan-count.sh`, in full

Copy this out, `chmod +x`, run it with no argument inside the repository or
pass a root. `--json` for diffing before against after; `--list` prints every
token it found per file, which is how you audit what it did and did not pick

```bash
#!/usr/bin/env bash
#
# exp26-plan-count.sh — the UI-revamp baseline measurement.
#
# ONE script, run before and after the revamp, on the same tree layout, so the
# 80 % claim is a subtraction rather than an estimate. It reads source only and
# writes nothing.
#
#   ./exp26-plan-count.sh [repo-root]        # human table
#   ./exp26-plan-count.sh --json [repo-root] # machine-readable, for diffing
#
# Metrics, per package, over SHIPPING files only (`*.test.*`, `*.stories.*` and
# `src/testing/**` are counted separately and reported on their own row):
#
#   a  component_files    .tsx files that export at least one Capitalised symbol
#      component_exports  those exported Capitalised symbols, counted
#      styling_files      source files carrying at least one class string —
#                         "files that make a styling decision". THIS is the
#                         number the "80 % fewer UI components" target is read
#                         against, outside @vpay/ui.
#   b  classname_sites    occurrences of `className` in the source
#   c  class_tokens       DISTINCT whitespace-separated tokens across every
#                         class string (definition below)
#      class_tokens_total the same, with duplicates, so churn is visible too
#   d  css_lines          non-blank, non-comment lines in every *.css in scope
#      apply_sites        occurrences of `@apply`
#   e  inline_styles      occurrences of `style={{`
#
# Two aggregate rows are printed under the table and are what the gate reads:
#   TOTAL (shipping)          every scope, @vpay/ui included
#   OUTSIDE @vpay/ui          every scope but the shared library. `class_tokens
#                             _distinct` there is a UNION across packages, not
#                             a sum, so a token used by two apps counts once.
#
# KNOWN BLIND SPOT, stated so the numbers are not oversold: a class name held in
# a plain lookup object that is not an argument to cva/cn/clsx/twMerge is not
# seen. At the 2026-09-07 baseline that is exactly three tokens — `alert-success`
# `alert-error` `alert-info` in `TONE_CLASS` in
# frontends/apps/checkout/src/components/screens.tsx. The revamp moves that map
# into a `cva` variant, where this script DOES see it, so the blind spot makes
# the "after" number bigger rather than smaller. The measurement is therefore
# conservative against the reduction being claimed.
#
# A "class string" is deliberately narrow and mechanical, so two people get the
# same number:
#   - the value of a `className=` attribute — "…", '…', {'…'}, {"…"}, or a
#     template literal with every `${…}` deleted; and
#   - every string literal lexically inside a `cva(`, `cn(`, `clsx(` or
#     `twMerge(` call (balanced parens).
# Nothing else. A class name assembled at runtime out of a lookup table that is
# not inside one of those calls is NOT counted — `--list` prints every token so
# a reader can see exactly what was and was not picked up.
#
set -euo pipefail

json=0
list=0
root=""
for arg in "$@"; do

    --json) json=1 ;;
    --list) list=1 ;;

const SKIP_DIR = new Set(['node_modules', '.next', 'dist', 'storybook-static', '.turbo', 'zenstack', '.zenstack']);

function walk(dir, out = []) {
  let entries;
  try { entries = readdirSync(dir); } catch { return out; }
  for (const name of entries) {
    if (SKIP_DIR.has(name)) continue;

const isSource = (f) => /\.(tsx|ts|jsx|js)$/.test(f) && !/\.d\.ts$/.test(f);

const isNonShipping = (f) =>

/** Delete `${ … }` from a template literal body, leaving only its literal text. */
function stripInterpolations(s) {
  let out = '';
  for (let i = 0; i < s.length; i++) {
    if (s[i] === '$' && s[i + 1] === '{') {
      let depth = 1;
      i += 2;
      while (i < s.length && depth > 0) {
        if (s[i] === '{') depth++;
        else if (s[i] === '}') depth--;
        i++;
      }
      i--;
      out += ' ';
    } else out += s[i];
  }
  return out;
}

/** The slice from `open` (index of the `(`) to its matching `)`. */
function balanced(src, open) {
  let depth = 0;
  for (let i = open; i < src.length; i++) {
    if (src[i] === '(') depth++;
    else if (src[i] === ')') { depth--; if (depth === 0) return src.slice(open + 1, i); }
  }
  return src.slice(open + 1);
}

const STRING_LITERAL = /'([^'\\\n]*(?:\\.[^'\\\n]*)*)'|"([^"\\\n]*(?:\\.[^"\\\n]*)*)"|`([^`\\]*(?:\\.[^`\\]*)*)`/g;

function classStrings(src) {
  const found = [];

  // 1. className= attributes.
  const attr = /className\s*=\s*(\{?)/g;
  let m;
  while ((m = attr.exec(src)) !== null) {
    const rest = src.slice(m.index + m[0].length);
    const q = rest[0];
    if (q === '"' || q === "'" || q === '`') {
      const close = q === '`' ? /`/ : new RegExp(q);
      const end = rest.slice(1).search(close);
      if (end >= 0) {
        const body = rest.slice(1, 1 + end);
        found.push(q === '`' ? stripInterpolations(body) : body);
      }
    }
  }

  // 2. every string literal inside cva( / cn( / clsx( / twMerge(.
  const call = /\b(cva|cn|clsx|twMerge)\s*\(/g;
  while ((m = call.exec(src)) !== null) {
    const body = balanced(src, m.index + m[0].length - 1);
    let s;
    const re = new RegExp(STRING_LITERAL.source, 'g');
    while ((s = re.exec(body)) !== null) {
      const lit = s[1] ?? s[2] ?? s[3] ?? '';
      found.push(s[3] !== undefined ? stripInterpolations(lit) : lit);
    }
  }

  return found;
}

/** Exported symbols whose name starts with a capital — the component surface. */
function componentExports(src) {
  const names = new Set();
  const re = /export\s+(?:default\s+)?(?:async\s+)?(?:function|const|class)\s+([A-Z][A-Za-z0-9_]*)/g;
  let m;
  while ((m = re.exec(src)) !== null) names.add(m[1]);
  const reExport = /export\s*\{([^}]*)\}/g;
  while ((m = reExport.exec(src)) !== null) {
    for (const part of m[1].split(',')) {
      const name = part.trim().split(/\s+as\s+/).pop()?.trim() ?? '';
      // `type Foo` re-exports are types, not components.
      if (/^[A-Z][A-Za-z0-9_]*$/.test(name) && !/^\s*type\s/.test(part)) names.add(name);
    }
  }
  return names;
}

const countOf = (src, re) => (src.match(re) ?? []).length;

  return src
    .replace(/\/\*[\s\S]*?\*\//g, '')
    .split('\n')
    .filter((l) => l.trim() !== '')
```
